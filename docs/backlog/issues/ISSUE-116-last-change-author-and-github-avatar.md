# Show the latest change's Git author and GitHub avatar in Details

- Status: In progress
- Assignee: Codex
- Priority: P2
- Area: Publish-time artifact attribution / reader Details

## Problem

Details currently identifies the latest relevant change by its Git committer name. GitHub can commit a person's squash commit as `GitHub` (web-flow), so readers see the service instead of the author. The owner requested the person's name and real GitHub avatar on 2026-10-19. ISSUE-114's byline work is in progress in another worktree and currently uses an initial-letter circle because the index has no avatar information.

This is a correctness problem in reader metadata, outside P1's core-workflow disruption. This issue delivers the publisher/index contract and fixtures; reader consumption follows separately. Do not edit `web/` or take over ISSUE-114.

## Evidence and reproduction

1. In a repository with a tracked publishable document, make its latest relevant commit with different author and committer identities, for example author `Alice Example` and committer `GitHub`.
2. Build its site index and inspect that artifact's `lastCommitter.name`.
3. The current implementation emits `GitHub`; there is no account or avatar field. A reader using that name therefore identifies the service.

Confirmed in source on 2026-10-19:

- [`build.go`](../../../cli/internal/indexer/build.go): `readArtifactGitHistory` reads `%ct`, `%cn`, `%H`; `ArtifactCommitter` contains only `name`. The newest committer timestamp wins. The document/resource ownership calculation is `artifactPathsForFile`.
- [`prepare.go`](../../../cli/internal/indexer/prepare.go) fingerprints the resolved name; working-tree changes can advance `updatedAt` while retaining the committed identity.
- [`history.go`](../../../cli/internal/indexer/history.go) and [`site_publish_prior.go`](../../../cli/internal/publisher/site_publish_prior.go) carry deployed `updatedAt` and committer names through shallow builds. Simply changing `%cn` to `%an` would both mislabel the existing field and retain stale `GitHub` values during migration.
- [`actions/publish/action.yml`](../../../actions/publish/action.yml) already passes the workflow's `GITHUB_TOKEN` to the CLI. No new token input or permission beyond repository `contents: read` is needed.
- [Specification §8, Right sidebar](../../specification.md#right-sidebar) explicitly defines committer attribution, disclaims GitHub resolution, and excludes commit emails from the public index.

The reproduction above is a deterministic source-backed case, not a claim that a live production index was inspected. ISSUE-114's current byline state is owner-reported; its unmerged files are not present in this worktree.

## Expected outcome

A published artifact supplies the Git author of its latest relevant committed change, optionally enriched with the GitHub account associated with that exact commit. The byline can show that name and the account's avatar without a browser API lookup or exposing email. Missing associations remain missing. This is commit attribution, not proof of personal identity or a claim about the document's original author.

### Identity and history selection (settled)

- Add `lastAuthor`; its `name` is the selected commit's raw Git author name (`%an`, without mailmap substitution). Keep `lastCommitter.name` as the raw Git committer name (`%cn`) of that same commit. Do not relabel or overwrite `lastCommitter` with an author.
- Preserve the existing attribution scope: the document plus non-document resources assigned by the nearest containing document directory; a resource contributes only to documents which themselves have Git history. Do not replace this with referenced-resource analysis.
- Consider commits reachable from the checked-out `HEAD`, using full path history, with renames treated as deletion/addition. For each commit, relevant paths are its changed paths; for a merge compare its tree against its **first parent**, not all parents. A true root commit compares against the empty tree; a shallow boundary, including a merge whose first parent is unavailable, is not a true root (see the boundary rule below). Select the relevant commit with the greatest committer timestamp (`%ct`); equal timestamps choose the lexicographically smallest full lowercase commit SHA. Take author, committer and SHA together from this one selected commit. Author dates never choose the winner or replace `updatedAt`. This intentionally replaces the current first-in-`git log` tie behaviour: an equal-`%ct` tie may select a different commit and therefore different `lastCommitter`/`lastAuthor`. This compatibility change to the commit selection underlying `updatedAt` and `lastCommitter` is accepted; the numeric Git contribution to `updatedAt` is unchanged by the tie itself because the timestamps are equal (merge inclusion can independently advance it).
- This explicitly includes a merge's first-parent changes (including conflict resolutions), unlike the current default log's omitted merge diffs. A merge with no first-parent changes contributes nothing. For a normal merge, the merge commit's Git author is the attribution, commonly the person merging; do not claim that person wrote each imported line. Do not look through a selected merge to substitute the PR author.
- A squash is one commit: use its primary Git author. Rebase/fast-forward commits use their recorded Git authors. Ignore `Co-authored-by` trailers for this single-person byline; never select the workflow actor, PR opener, reviewer, merger API identity, or token owner instead of the selected Git author.
- Keep bot authors, including bot-authored squash/merge commits, as bots. Do not skip automation to find an earlier human or substitute a co-author. A GitHub association for a bot may supply the bot's real avatar. If Git records the author itself as `GitHub`, retain that name rather than inventing a human.
- `updatedAt` retains the existing commit-time/working-tree/mtime precedence, using the selected commit above as its Git contribution. For a tracked document with local edits, `lastAuthor` and `lastCommitter` still describe the latest committed change even when the displayed update time comes from local files. Untracked/ignored generated documents without their own history have neither identity field, even if adjacent resources have history. Omit `lastAuthor` if its Git name is empty/whitespace; never fall back to email or an inferred human.

### Public JSON contract (settled)

Keep artifact-index `schemaVersion: 1`. Add only the optional artifact field below; registry, discovery metadata, full-text and preview formats do not change. Example fragment (the SHA is illustrative):

~~~json
{
  "updatedAt": "2026-10-19T00:00:00Z",
  "lastCommitter": { "name": "GitHub" },
  "lastAuthor": {
    "name": "Alice Example",
    "commitSha": "0123456789abcdef0123456789abcdef01234567",
    "github": {
      "login": "octocat",
      "avatarUrl": "https://avatars.githubusercontent.com/u/1?v=4"
    }
  }
}
~~~

`lastAuthor.name` and `lastAuthor.commitSha` are required when the object exists. `commitSha` is the full lowercase object ID of the selected commit (40 hex for SHA-1, 64 for SHA-256 repositories), not `HEAD` unless it won selection. `github` is optional; when present, its `login` is required and its `avatarUrl` is optional. Missing values are omitted, not `null` or empty strings. No `email`, email hash, profile display name, profile URL, bot flag, or co-author list is added. The Git name remains the display name even when the GitHub login differs.

### GitHub enrichment, privacy and availability (settled)

- Resolve only GitHub.com repositories. Require the effective source repository URL to identify `https://github.com/<owner>/<repo>` and the checkout's `origin` (HTTPS or SSH) to identify that same repository, case-insensitively. Metadata overrides alone must not cause credentialed requests to another repository. Other hosts, including GitHub Enterprise Server, receive Git names/SHA only; never send their data or credentials to GitHub.com.
- Use the first nonempty `GITHUB_TOKEN`, then `GH_TOKEN`, for `GET https://api.github.com/repos/{owner}/{repo}/commits/{full-SHA}?per_page=1`, with JSON accept headers and `X-GitHub-Api-Version: 2022-11-28`. This matches the existing config, preview and bootstrap GitHub requests; the required commit/account fields are available in this supported version. A CLI-wide API-version upgrade is separate work, not part of this feature. No unauthenticated requests, interactive login, new CLI flag, config key, Action input, PAT requirement, or account-search endpoint. Standalone/local builds with neither token perform no enrichment requests. The existing Git-depth fetch credential rules remain separate; `ARTIFACT_PAGES_FETCH_TOKEN` is not an enrichment credential.
- Accept only HTTP 200 with a response `sha` matching the requested SHA and a non-null **top-level `author`** account. Its `login` supplies `github.login`; its `avatar_url` supplies `github.avatarUrl`. Do not use top-level `committer`, nested `commit.author.email`, or a user profile's display name. A null author or blank/invalid login leaves `github` absent. Accept logins consisting of ASCII letters, digits and hyphens, optionally ending in `[bot]`, with no whitespace or URL syntax.
- Accept an avatar URL only when it is HTTPS, host exactly `avatars.githubusercontent.com`, with no credentials, fragment or nonstandard port, and a nonempty absolute path. Preserve its returned path/query; do not construct a URL from a name, login, numeric ID or email. Invalid/missing avatar means login only. The later reader applies the same URL policy. Reject redirects for API requests, and never attach the API token to an avatar request.
- Do not parse even GitHub noreply addresses to infer a login or construct an avatar. Both `ID+LOGIN@users.noreply.github.com` and legacy `LOGIN@users.noreply.github.com` require the same commit API association; Git strings alone are not account verification. Ordinary/private author emails need no special handling because lookup is by repository and SHA. Do not send email search queries, use Gravatar, or publish raw API responses. Discard email fields; do not persist emails, email hashes, tokens or response bodies in public indexes, private state, fixtures or diagnostics.
- Enrich each distinct missing `(repository, commitSha)` at most once per invocation, shared across artifacts. “Missing” means no validated `github.login`, or a validated login without a validated avatar URL, after eligible prior-snapshot reuse; a validated login/avatar pair is complete and is not requested again. Sort missing SHAs lexicographically; make requests sequentially, at most 100 requests and 30 seconds total, with a 5-second per-request timeout and a 1 MiB response-body cap. No pagination, automatic retries or sleeping until quota resets: only the first page's commit/account metadata is used.
- A 404/422, null author, invalid response or oversize response omits that SHA's enrichment and continues within the budget. A 401/403/429, exhausted rate-limit header, transport failure, timeout or 5xx stops further enrichment for this invocation. Do not publish guessed replacements. Preserve any valid results already obtained; unresolved commits still publish their Git name/SHA. Emit at most one sanitized warning summarizing lookup failures/budget omissions and counts; a deliberately missing token, unsupported host or null author is normal absence. Enrichment failure never fails an otherwise valid build/sync or changes its exit code; parent-context cancellation still cancels the command.
- The publish Action uses its existing workflow token with `contents: read`; no settings or permission changes are part of this issue. A direct CLI caller can provide either supported token environment variable. Dry-run may perform these read-only lookups under the same limits and never writes a cache or changes provider state.

GitHub's [API version documentation](https://docs.github.com/en/rest/about-the-rest-api/api-versions) lists `2022-11-28` as supported through 2028-03-10. GitHub's [commit endpoint](https://docs.github.com/en/rest/commits/commits#get-a-commit) distinguishes the Git metadata from the associated top-level account and supports repository contents-read access. Its [rate-limit documentation](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github_token-in-github-actions) documents a shared workflow-token quota; the bounds above are this product's own smaller work budget, not a promise of available quota. GitHub also documents [both noreply formats](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference).

### Migration, shallow history and compatibility (settled)

- Treat `lastAuthor` as additive under specification §5.3: older readers ignore it and continue using `lastCommitter`; newer readers accept old indexes without it. Do not bump the public index schema or redefine a required field. The CLI's artifact-index compatibility declaration remains version 1.
- Advance the prepared-build input policy to 4 (superseding main’s policy 2 and the provisional policy 3 in implementation commit `d3254482`). Fingerprint the selected Git author name and full commit SHA alongside existing Git-derived metadata and other publish inputs, but exclude `lastAuthor.github`, token presence/value and API outcomes. Migration must not take either older policy’s input-root no-op and skip the new contract. Resolve enrichment only after the ordinary no-op decision, or for explicit reconciliation/standalone builds; freeze the resulting association once for rendering/reconciliation without another API call. The committed input root identifies deterministic publish inputs and policy, not every optional output snapshot; committed object digests still cover the complete emitted index, including enrichment.
- Carry forward the complete author object, SHA and committer together only from a digest-verified deployed index produced under this selection contract, with the existing unchanged-attribution-scope rules. A visible candidate replaces the prior selection when it wins the timestamp/SHA ordering above, including an equal-timestamp tie. A valid `lastAuthor` is evidence of the new selection contract. An entry without a valid `lastAuthor` cannot establish this selection contract: recompute it from Git, deepening/unshallowing by the existing rules as needed, even when its files are unchanged. This includes both legacy committer-only entries and new-writer entries deliberately omitting an empty/whitespace author name. They are intentionally indistinguishable: accept repeated Git derivation on later invocations, with possible history fetching in a fresh shallow checkout. Do not add an omission marker, sentinel author or private-state field. Repeated derivation does not itself force republication when the prepared fingerprint is unchanged. Do not copy `lastCommitter.name` into `lastAuthor` or trust shallow boundary commits. Preserve the existing documented byte-identical-history limitation.
- Existing shallow-boundary handling applies to first-parent merge selection too. Consult the shallow-boundary set, not just the parents exposed by traversal: Git can present a boundary as parentless even when the commit object records parents. Never attribute a boundary commit, apply the true-root empty-tree rule to it, or treat an unavailable first-parent diff as an empty merge. Conservatively treat files present in the boundary tree as possible touches and propagate them through the existing attribution-scope calculation. Unless eligible unchanged-scope carry-forward applies, a visible non-boundary candidate must be strictly newer than every touching boundary timestamp; an equal timestamp remains ambiguous regardless of SHA tie-break. Otherwise deepen/unshallow and recompute by the existing steps and fetch-failure rules. Once the first parent is available and the commit is no longer a boundary, evaluate its actual first-parent changes normally.
- For both full and shallow site sync, reuse validated GitHub enrichment from that trusted prior index only when repository and selected commit SHA still match. The prior repository comes from that artifact entry’s `source.repositoryUrl` in the digest-verified deployed index, not from `lastAuthor`, the current registry or an assumed site identity. Normalize it to a GitHub.com owner/repository and compare case-insensitively with the current effective source repository and checkout `origin` under the enrichment eligibility rule above; compare the prior `lastAuthor.commitSha` with the currently selected full SHA. Missing, invalid, unsupported or mismatched prior source identity disables account-snapshot reuse; do not fall back to `source.repository` or infer it from the matching SHA. No new public repository field is needed.
- This is a published association snapshot, not a live profile directory; keep it while the repository and selected commit still match. Do not refresh a complete validated login/avatar pair each run. A login-only association remains eligible to fill its missing avatar. Retry missing login/avatar data on later eligible enrichment passes within the same budget (for site sync: changed-input publication or explicit `--reconcile`; for standalone builds: each build), including after HTTP 200 with a null top-level author (normal absence), invalid data, lookup failure or budget omission. Persist no negative-result marker: normal absence suppresses warnings, not future lookup eligibility. Within one invocation a null/failed result is still deduplicated across all artifacts and is not retried. An omitted blank-name `lastAuthor` is not an enrichment candidate.
- An unsuccessful retry retains any already validated login. When filling a missing avatar, replace the account pair only with a valid login and avatar from the same successful response; never combine components from different accounts. With no trusted snapshot, a tokenless/offline build has no GitHub enrichment. Git name/SHA remain derivable offline from sufficient local history; avatar completeness is not a full-clone equivalence guarantee.
- Prior-index readers must check schema before consuming fields, retain digest/HTTP-metadata validation for plain and gzip indexes, and ignore unknown fields. A malformed optional author object cannot be carried forward: re-derive its Git identity; a malformed optional account/avatar is unavailable and may be resolved again. The later web reader similarly treats invalid optional attribution as absent rather than rejecting the site. Unsupported schemas/control formats still fail closed before projection writes under §5.3; enrichment's optional failure policy does not bypass those checks.
- No object key, HTTP policy, private-state layout or required state field changes. Keep private publish-state schema 1. [IMP-77](../implementation/IMP-77-fulltext-section-table-and-text-packs.md)'s older-CLI failure came from newly unsupported search-object keys; that mechanism is **not relevant** to this additive metadata. Do not claim older CLIs will reject `lastAuthor`: they may ignore/drop it on a subsequent sync. During 0.x, operators pin one CLI per site and use the new writer to preserve the feature; a rollback can remove attribution enrichment and the reader falls back. Existing unsupported-version checks must remain intact. No release, deploy or operator-repository mutation is authorized by this ticket.

### No-op and request-cost decision (settled, 2026-10-20)

This amendment supersedes the earlier complete-author fingerprint and every-invocation retry requirements. Choose option 2: preserve specification §5.3’s existing no-op request budgets and defer optional account enrichment until after that decision. Option 1 would weaken the published request-cost contract; option 3 would change the expressly excluded private-state layout. Neither is authorized by this issue.

- For an ordinary matching reusable-input publish with sufficient local Git history, supported state, no pending origin transaction and no other publication duty: AWS/default HEAD-first state HEAD/GET/PUT is **1/0/0**; R2/GET-only is **0/1/0**. Both have **zero projection HEAD/GET/LIST/PUT/DELETE**, zero enrichment API requests, no build and no cache invalidation. Registry, compatibility, lock, journal and preview checks retain their existing separate control budgets; these numbers are not whole-command totals.
- Do not load a prior index solely to reproduce enrichment before the no-op decision, even when a complete association may already exist. An ordinary no-op preserves the deployed index and its association without reading or rewriting it. Adding/removing a token, a GitHub profile change, null-author retry eligibility or an incomplete pair alone does not invalidate this no-op. Missing associations may therefore stay missing until an input change or explicit reconciliation. Standalone builds have no publisher no-op and retain their bounded lookup behavior.
- After an input mismatch, or with `--reconcile`, read the digest-verified prior index as needed, reuse complete validated pairs for matching repository/SHA, then attempt only missing/incomplete pairs under the existing limits. Explicit reconciliation must run this enrichment pass even with a matching input root; a successful missing-pair fill can update the index and committed inventory while retaining that root. A failed/absent lookup retains valid prior data and does not itself require projection writes. Complete pairs are never refreshed, including during reconciliation. No new flag, state field, cache or negative-result marker is introduced.
- Keep the existing shallow-history exception: resolving ambiguous Git attribution may require prior state/index reads and Git deepening before a reusable input root is known. This is not permission to read prior indexes for enrichment on every full-history publish, nor a promise to eliminate existing shallow carry-forward reads. Reuse any already validated snapshot in the later enrichment pass.
- The publisher must share one invocation’s state observation across attribution and publication planning: R2 reads state once; HEAD-first readers GET the body at most once when needed, checking its ETag against the preceding HEAD before trusting the body or performing projection writes. With changed inputs, state HEAD/GET/PUT remains **1/1/1** for AWS and **0/1/1** for R2 on successful commit. The HEAD/GET ETag-mismatch case remains one state GET and zero state/projection writes. Preserve journal ordering, generation/CAS checks, digest/HTTP-metadata/schema validation, and mandatory pending-work handling.
- Do not relax any assertions in `TestPublishSiteWholeControlRequestsCompareR2GetOnlyAndAWSHeadThenGet`, `TestPublishSiteNoOpSkipsBuildManifestAndProjectionInventory`, `TestPublishSiteGetOnlyStatePolicyUsesCompleteGetMetadata`, or `TestPublishSiteChangedStateETagBetweenHeadAndGetFailsBeforeProjectionWrites`. Reuse fetched prior-index data for generatedAt preservation rather than adding duplicate reads; this decision grants no changed-path request-budget increase. Update ISSUE-116-specific fingerprint/policy/retry expectations and add coverage of enriched tokenless no-ops, missing-pair no-ops, changed-input fills and same-root reconciliation fills.

### Reader handoff (behaviour for a later web ticket)

- In the production Details byline, prefer valid `lastAuthor.name`; otherwise retain `lastCommitter.name` as the legacy fallback. If neither exists, omit the identity/name/avatar portion and retain the available Updated date. Do not label the preferred identity “Last committed by”; use the name with “Updated <date>”, as in ISSUE-114. The date always uses artifact `updatedAt`, never API/profile time or index `generatedAt`.
- Use only `lastAuthor.github.avatarUrl` under the URL policy above. No browser-side GitHub API calls or derived avatar URLs. When the URL is absent/invalid, fails to load, or is blocked, use the existing initial-letter fallback from the displayed name. An avatar failure must not prevent reading, show a broken-image icon, or change the name/date. Request avatars without credentials and with `referrerPolicy="no-referrer"`; the remote image request reveals the reader's IP to the avatar host. Do not proxy/download avatars into the static projection in this slice.
- The avatar is decorative beside the visible name (empty alt text). Login is metadata, not a replacement display name or a new profile link. Never pair a legacy committer fallback with an unrelated author avatar. Preview Details remain unchanged; no production attribution is inferred for preview documents.
