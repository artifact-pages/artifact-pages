Before you publish

Access and trust

Two decisions come before the first publish: whose HTML you trust, and who may read. Git Artifact Pages makes neither for you. This page explains what it does and does not do, and where each decision belongs.

Summary

TRUST · WHAT YOU PUBLISH

Publishing HTML means running its code.

A published HTML page runs its own JavaScript for every reader, with the same access as the reader app. Publish only HTML you would be willing to run yourself. Markdown is different: it is cleaned, and its scripts never run.

ACCESS · WHO CAN READ

There are no logins. Gate the address.

Artifact Pages has no accounts and no per-site permissions. Anyone who can reach the delivery address can read every site there. To limit readers, put access control at the delivery edge or network.

HTML runs as published

An HTML page is shown in a frame inside the reader, exactly as published. The frame keeps the page's CSS separate from the app; it is not a security boundary. All sites share one address, so a page's scripts can reach far beyond the page itself.

  • Same access as the reader. Scripts in a published page can read and change the reader page, use the browser storage that holds pins and recent reads, and fetch other sites' published files on the same address.
  • External resources. Pages can load scripts, styles, images, fonts, and data from any HTTPS address, subject to the browser's usual rules. Plain http:// resources are blocked. Requests to other hosts carry ordinary request details, as on any website.
  • No isolation between sites. Artifact Pages does not protect one site from another site's HTML. Everyone who can publish HTML to any site on the address is trusted by the readers of all of them.
  • Previews too. Preview HTML runs the same way, before its review is finished. Previews from forks are not supported.

Markdown is cleaned before it is shown

Markdown is rendered by the reader itself, not run. That makes it the safer format when many people contribute.

What to publish, and what not to

  • Pages your team writes and reviews in Git like code.
  • Reports and diagrams that your own CI generates from reviewed code.
  • Markdown from a wider group of contributors; it cannot run scripts.
  • HTML or JavaScript you have not reviewed, from people or tools you do not trust.
  • Secrets, tokens, and internal-only notes. Every file in the published directory can be fetched, even if no page links to it.
  • Content that must stay private, unless access control at the edge already covers the whole address.

Who may publish is decided in Git and in your CI: who can merge to the publishing branch, and which jobs hold publishing credentials. Treat those permissions like permission to deploy code.

Who can read

Artifact Pages has no accounts, sign-in, roles, or per-site permissions. Once a request reaches it, everyone gets the same pages. Limiting readers is done in front of it, by whoever operates the delivery address.

  • Choose a mechanism your hosting supports, for example a VPN or IP allowlist, Basic Authentication, an identity provider with CloudFront signed cookies, or Cloudflare Access.
  • Choose its scope. It can protect the whole hostname, selected paths, or a wider network. That choice lives in your infrastructure, not in artifact-pages.yaml, the site registry, or the reader.
  • Make it run before anything is served, including responses from a shared cache.
  • Verify it yourself. Artifact Pages cannot tell whether a gate is in place.

Taking content down

Delete the file and publish again, or unregister the whole site (see Configuration). Both delete the files at the origin and ask the CDN to refresh. A cache may still serve the old copy for a short time, and pages a reader already opened or saved cannot be recalled. The file also remains in Git history. If a secret was published, treat it as exposed and replace it.

Previews keep their own copy. A preview revision that contained the file is not changed by deleting the file and publishing again. Its entry may leave the preview list, but its direct URL keeps working until the delivery target's retention rule deletes it (see Previews). Only unregistering the site deletes its previews at once. If a leaked secret was ever in a preview, assume it can still be read from that URL until then.
