Independent publishing, shared experience

Publish from each repository. Read in one place.

Make and review artifacts in Git, and publish them team by team. No central build assembles every site. Each team publishes only its own site, from its own repository and CI. Published sites land on one shared static delivery target, and readers use one reader app to choose a site, find a page, read it, and share a link, the same way on every site.

Readers pick pages from the sidebar, search with ⌘K / Ctrl K, and switch sites with @. (Enable JavaScript to see it in motion here.)

The sample uses this guide's own pages plus illustrative examples.

01
Git is the source

Artifacts are reviewed in the repository that made them and published with their Git history. Nothing is edited inside Artifact Pages. HTML and Markdown keep their filenames and extensions, at URLs like /site/file.html.

02
Each site publishes on its own

One directory in one Git repository becomes one site. Each site publishes only its own scope, from its own repository, when its content changes, without waiting for another site's build or deploy.

03
One place to read

Published sites share one static delivery target (object storage and a CDN) with no always-on server. Switching sites, search, contents, and links to Git work the same in one reader app on every site.

How it works

From publishing to reading

Four roles take a document from Git to a reader. The admin provides the shared reader app and registers sites; each team's repository does its own publishing. For what happens underneath, such as how files are stored and why no server runs per request, see the Architecture overview.

01 / DEPLOY THE APP Admin

First, deploy the reader app.

An admin deploys the static reader app (SPA) to the delivery target once. It is the shared entry point for every site. The command downloads and verifies a web release of the app, then writes only the application files.

TERMINAL / ADMIN
# Review the plan first (writes nothing)
$ artifact-pages app deploy --dry-run
# Apply
$ artifact-pages app deploy

app deploy installs the reader app of the same version as the CLI you run (x.y.z); to install a different app version, use that version's CLI. Releases are listed on GitHub Releases. The delivery target comes from --config or the admin repository's artifact-pages.yaml. Site indexes and documents are left untouched.

02 / REGISTER SITES Admin

Next, register the sites.

A site per team is the usual starting point, and one team can split sites by product. Each site has an ID, a display name, a source Git repository (owner/repo), and a directory (sourcePath). The admin lists them in the config file and registers them. A site can be registered before it has any documents.

artifact-pages.yaml / ADMIN REPOSITORY
sites:
  sre:
    name: SRE
    repository: acme/sre-handbook
    sourcePath: docs/public
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts
  billing:
    name: Payments / Billing
    repository: acme/billing
    sourcePath: docs/artifacts
TERMINAL / ADMIN
$ artifact-pages registry register --dry-run
$ artifact-pages registry register

The sites mapping is the complete set of sites to register. A site removed from it is unregistered by the next registry register, and its published content is deleted. Delivery target (provider) settings are omitted here.

03 / PUBLISH FROM GIT Team repositories

Publish from each Git repository to its site.

Each team's Git repository publishes with an explicit site and source directory. Every publish builds the index and places HTML, Markdown, CSS, and images as they are.

Publishing is independent per site. No central build assembles every site: each repository publishes only its own site, from its own CI, when its content changes, and never waits for another site to publish.

TERMINAL / acme/checkout
# docs/artifacts to the checkout site
$ artifact-pages site publish --site checkout --source docs/artifacts --dry-run
$ artifact-pages site publish --site checkout --source docs/artifacts

Before writing, the publisher checks that the repository and directory match the registration on the delivery target. It never writes to another site. Running the same command from CI on merge is the expected workflow.

04 / OPEN AND FIND Reader

Then just open the URL to read.

All a reader needs is a browser. While reading, ⌘K / Ctrl K finds pages in the current site and headings in the open page, and @ switches to another team's site.

URLs keep filenames and extensions, so links to documents can be shared as they are. <delivery-domain> is the address the admin chose for the delivery target. Reading covers the screen and search in detail.
