From Git to a readable website

A reading place for the work you keep in Git.

Keep HTML and Markdown in Git, and read them by URL with search. Git Artifact Pages publishes documents managed in Git as a static site, giving readers one place to choose a site, find a page, and share a link.

Readers pick pages from the sidebar, search with ⌘K / Ctrl K, and switch sites with @. (Enable JavaScript to see it in motion here.)

The sample uses this guide's own pages plus illustrative examples.

01
Publish as is

HTML and Markdown keep their filenames and extensions. URLs take the form /site/file.html, ready to share.

02
A site per team

Give each team or product its own reading space. One directory in one Git repository becomes one site.

03
Find it fast

Search pages with ⌘K / Ctrl K and switch sites with @. The index is built at publish time.

How it works

From publishing to reading

01 / DEPLOY THE APP Admin

First, deploy the reader app.

An admin deploys the static reader app (SPA) to the delivery target once. It is the shared entry point for every site. The command downloads and verifies a published web release, then writes only the application files.

TERMINAL / ADMIN
# Review the plan first (writes nothing)
$ artifact-pages app deploy --version x.y.z --dry-run
# Apply
$ artifact-pages app deploy --version x.y.z

Replace x.y.z with a published release version. The delivery target comes from --config or the admin repository's .artifact-pages.yaml. Site indexes and documents are left untouched.

02 / REGISTER SITES Admin

Next, register the sites.

A site per team is the usual starting point, and one team can split sites by product. Each site has an ID, a display name, a source Git repository (owner/repo), and a directory (sourcePath). The admin lists them in the config file and registers them. A site can be registered before it has any documents.

.artifact-pages.yaml / ADMIN REPOSITORY
sites:
  sre:
    name: SRE
    repository: acme/sre-handbook
    sourcePath: docs/public
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts
  billing:
    name: Payments / Billing
    repository: acme/billing
    sourcePath: docs/artifacts
TERMINAL / ADMIN
$ artifact-pages registry register --dry-run
$ artifact-pages registry register

The sites mapping is the complete set of sites to register. A site removed from it is unregistered by the next registry register, and its published content is deleted. Delivery target (provider) settings are omitted here.

03 / PUBLISH FROM GIT Team repositories

Publish from each Git repository to its site.

Each team's Git repository publishes with an explicit site and source directory. Every publish builds the index and places HTML, Markdown, CSS, and images as they are.

TERMINAL / acme/checkout
# docs/artifacts to the checkout site
$ artifact-pages site publish --site checkout --source docs/artifacts --dry-run
$ artifact-pages site publish --site checkout --source docs/artifacts

Before writing, the publisher checks that the repository and directory match the registration on the delivery target. It never writes to another site. In practice, CI runs the same command on merge.

04 / OPEN AND FIND Reader

Then read it at an ordinary URL.

Readers just open a URL. While reading, ⌘K / Ctrl K searches the current site's pages and headings, and @ switches to another team's site.

BROWSER / READER
→ https://<delivery-domain>/checkout/design/payment-flow.html
⌘K / Ctrl K   Search this site's pages and headings
@             Switch sites

URLs keep filenames and extensions, so links to documents can be shared as they are. <delivery-domain> is the address the admin chose for the delivery target.

Git is the source. The web is where you read.

Search, navigation, and pins exist for reading; content changes happen in Git. HTML is treated as a document from a trusted publisher, and viewer access control is configured at the delivery edge. The teams and repositories in the diagrams and config (acme/…) are illustrative.
