公開する前に

信頼とアクセス制御

最初に公開する前に、決めておくことが2つあります。誰のHTMLを信頼するかと、誰に読ませるかです。Git Artifact Pagesはどちらも代わりに決めてはくれません。このページでは、製品がすることとしないこと、それぞれをどこで決めるかを説明します。

要点

信頼：公開するもの

HTMLを公開することは、そのコードを動かすことです。

公開したHTMLのページは、読者全員のブラウザで、閲覧アプリと同じ権限のまま自分のJavaScriptを動かします。自分で実行してもよいと思えるHTMLだけを公開してください。Markdownは違います。表示する前に不要な要素を取り除き、スクリプトは動きません。

アクセス：読める人

ログインはありません。入口で制限します。

Git Artifact Pagesには、アカウントもサイトごとの権限もありません。配信先のアドレスに届く人は、そこにあるすべてのサイトを読めます。読める人を限るには、配信側やネットワークでアクセス制御を行います。

HTMLは公開したとおりに動く

HTMLのページは、閲覧アプリの中の枠（iframe）に、公開したとおりに表示されます。枠はページのCSSをアプリと分けるためのもので、安全のための境界ではありません。すべてのサイトが同じアドレスにあるので、ページのスクリプトはそのページの外にも手が届きます。

  • 閲覧アプリと同じ権限。公開したページのスクリプトは、閲覧アプリの画面を読んだり書き換えたりでき、ピン留めや最近読んだページを入れているブラウザの保存領域も使えます。同じアドレスにあるほかのサイトの公開ファイルも取得できます。
  • 外部のリソース。ページは、HTTPSのアドレスであればどこからでも、スクリプト、スタイル、画像、フォント、データを読み込めます（ブラウザの通常の制約には従います）。http://のリソースは読み込めません。ほかのホストへのリクエストには、ふつうのWebサイトと同じくリクエストの情報が付きます。
  • サイトどうしは分離されていません。あるサイトのHTMLから、別のサイトを守るしくみはありません。そのアドレスのどこかのサイトにHTMLを公開できる人は、すべてのサイトの読者から信頼されていることになります。
  • プレビューも同じです。プレビューのHTMLも、レビューが終わる前から同じように動きます。フォークからのプレビューには対応していません。

Markdownは表示する前に無害化される

Markdownは閲覧アプリが整えて表示するもので、コードとしては動きません。多くの人が書く文書には、こちらのほうが安全です。

公開してよいもの、いけないもの

  • チームが書き、コードと同じようにGitでレビューしたページ。
  • レビュー済みのコードから、自分たちのCIが生成したレポートや図。
  • 多くの人が書くMarkdown。スクリプトは動きません。
  • レビューしていないHTMLやJavaScript。信頼できない人やツールが作ったもの。
  • 秘密情報、トークン、社内限りのメモ。公開したディレクトリのファイルは、どのページからもリンクされていなくても取得できます。
  • 人に見せてはいけない内容。配信側のアクセス制御がアドレス全体をすでに覆っている場合を除きます。

誰が公開できるかは、GitとCIの設定で決まります。公開するブランチへマージできる人と、公開用の認証情報を持つCIのジョブです。これらの権限は、コードをデプロイする権限と同じように扱ってください。

読める人を限る

Git Artifact Pagesには、アカウント、サインイン、役割、サイトごとの権限がありません。リクエストが届けば、誰にでも同じページを返します。読める人を限るのは、その手前で、配信先のアドレスを運用する人が行います。

  • 配信環境で使える方法を選びます。たとえば、VPNやIPアドレスの許可リスト、Basic認証、IDプロバイダーとCloudFrontの署名付きCookieの組み合わせ、Cloudflare Accessなどです。
  • 範囲を決めます。ホスト名全体、一部のパス、もっと広いネットワークのどれを守るかを選べます。この設定はインフラ側で行い、artifact-pages.yaml、サイトの登録情報、閲覧アプリには書きません。
  • 何かを返す前に効くようにします。共有キャッシュから返す応答も含みます。
  • 自分で確かめます。アクセス制御が入っているかどうかを、Git Artifact Pagesは判断できません。

公開した内容を取り下げる

ファイルを消してsite syncを再実行するか、管理者の設定ファイルのsitesからサイトを外してregistry syncを実行します（「設定ファイル」を参照）。どちらも対象の配信元ファイルを削除し、CDNにキャッシュの更新を依頼します。それでも、しばらくは古いコピーがキャッシュから返ることがあり、読者がすでに開いたり保存したりしたページは取り消せません。ファイルはGitの履歴にも残ります。秘密情報を公開してしまったときは、漏れたものとして扱い、新しいものに取り替えてください。

プレビューには別のコピーが残ります。ファイルを消してsite syncを再実行しても、そのファイルを含むプレビューは変わりません。プレビューの一覧からは消えることがありますが、プレビューのURLを直接開けば、配信先の保持ルールで削除されるまで読めます（「サイトの公開」のプレビューを参照）。preview remove --site checkout --group pr:42を使うと、そのグループを削除できます。サイトをレジストリから外すと、そのサイトのプレビューもすべて削除されます。漏れた秘密情報がプレビューに入っていたなら、それまではそのURLから読めるものと考えてください。

理由

理由を知りたいときは、Architectureサイトの「信頼モデル」を読んでください。HTMLを同じオリジンで動かす理由、リソースの規則がサイトごとにどう効くか、閲覧者の識別を配信側に任せる理由を説明しています。
