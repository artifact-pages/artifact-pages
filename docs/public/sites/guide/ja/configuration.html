管理者向け

設定ファイル

artifact-pagesのコマンドは、どれも1つのYAMLの設定ファイルを読みます。ふつうは管理リポジトリにあるartifact-pages.yamlです。配信先と、登録コマンドで使うサイトの定義をここに書きます。

ファイルの全体像

1つのファイルに、どこへ配信するか（プロバイダーとその設定）と、どのサイトがあるか（sites）の2種類を書きます。秘密の値は書きません。認証情報は環境変数から渡します。

artifact-pages.yaml / 管理リポジトリ
schemaVersion: 1             # 常に整数の 1
provider: local              # local、aws、cloudflare のいずれか
local:                       # そのプロバイダーの設定だけを書く
  root: .local/storage
sites:                       # 登録するサイトの全部
  checkout:
    name: 決済チーム / Checkout
    description: 決済画面とAPIの設計、障害対応、運用手順。
    repository: acme/checkout
    sourcePath: docs/artifacts
キー意味
schemaVersion必須整数の1。
provider必須配信先の種類。local、aws、cloudflareのいずれか。共通部分だけを書いた土台のファイルでは省略できます（重ね合わせ）。
local / aws / cloudflare必須providerに対応する設定のブロックを1つだけ書きます。配信先を参照してください。
sites任意あるべきサイトのすべて。サイトIDをキーにします。registry syncでは必須です。sitesを参照してください。

ファイルは厳密に検査されます。知らないキー、重複したキー、複数のYAMLドキュメント、型の違う値は、無視されずにエラーになります。例のサイトは説明用です。

使われるファイルの決まり方

コマンドは次の順に設定を探し、最初に見つかったものを使います。明示して指定するなら、ファイル名はartifact-pages.yamlでなくてもかまいません。

  1. --config LOCATOR

    ローカルのパスか、github://の指定。繰り返し指定すると、ローカルのファイルを重ね合わせます。

  2. ARTIFACT_PAGES_CONFIG

    指定を1つ入れた環境変数。

  3. いまのディレクトリのartifact-pages.yaml

    既定のファイル。管理リポジトリで実行するなら、オプションはいりません。

  4. 保存した既定の指定

    artifact-pages config set-default LOCATORで、ユーザーの設定ディレクトリに指定を1つ保存できます。保存されるのはこの指定だけで、認証情報は保存されません。

配信先を使うコマンドは、使った配信先（バケットなど）を出力に表示します。どの配信先に対して実行したかを確かめられます。

重ね合わせ

同じサイトの定義を、別の配信先でも使いたいことがあります。そのときはsitesを共通のファイルに、配信先を別のファイルに書き、--configで順に渡します。

artifact-pages.yaml / 共通
schemaVersion: 1
sites:
  checkout:
    name: 決済チーム / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts
.local/artifact-pages.local.yaml / コミットしない
schemaVersion: 1
provider: local
local:
  root: .local/storage
ターミナル / 管理者
$ artifact-pages registry sync --config artifact-pages.yaml --config .local/artifact-pages.local.yaml --dry-run
  • どのファイルにもschemaVersion: 1を書きます。providerを書いたファイルには、対応するブロックも1つだけ書きます。
  • あとのファイルの配信先は、前の配信先をまるごと置き換えます。プロバイダーの設定が混ざることはありません。
  • あとのファイルにsitesがなければ、前の一覧を引き継ぎます。sitesがあれば、{}であっても一覧全体を置き換えます。サイト単位で混ざることはありません。
  • 重ね合わせになるのは、--configを繰り返したときだけです。上書き用のファイルを自動で探すことはありません。

リモートの設定ファイル

チームのリポジトリでは、管理リポジトリのファイルを写さずにそのまま使えます。--configに、コミットを固定したgithub://の指定を渡します。

ターミナル / acme/checkout
$ artifact-pages site sync --site checkout --source docs/artifacts --config 'github://acme/platform-admin/artifact-pages.yaml?ref=0123456789abcdef0123456789abcdef01234567' --dry-run
  • 形式はgithub://OWNER/REPO/FILE?ref=REFです。FILEを省くとartifact-pages.yamlを読みます。refを省くと、デフォルトブランチをその時点のコミットに決め、コマンドの最後までそのコミットを使います。CIでは、実行の途中で配信先が変わらないよう、コミットのSHAを完全な形で固定してください。
  • ?を含むので、シェルではクォートで囲みます。プライベートリポジトリはGITHUB_TOKENかGH_TOKENで読みます。
  • ファイルは実行のたびに取り直し、使ったコミットを出力に表示します。
  • リモートの設定ファイルは、それだけで完結している必要があります。ほかのファイルとは重ねられません。
  • この指定で決まるのは配信先だけです。そのリポジトリがサイトに公開してよいかどうかは、配信先にある登録情報で判断します。

acme/platform-adminは説明用の管理リポジトリです。

配信先

プロバイダーのブロックには、閲覧アプリと公開したサイトを置く場所を書きます。サイト、URL、コマンドは、どのプロバイダーでも同じです。

local：ローカルのディレクトリ

手元のディレクトリに書き出します。開発や、試しに動かすときに使い、ローカルのWebサーバーで配信します。

キー意味
root必須書き出し先のディレクトリ。たとえば.local/storage。サイトの公開元のディレクトリと重なってはいけません。

aws：S3とCloudFront

artifact-pages.yaml / AWS
provider: aws
aws:
  region: ap-northeast-1
  accountId: "123456789012"     # バケットは artifact-pages-123456789012-ap-northeast-1
  distributionId: E1234567890ABC
キー意味
region必須バケットのあるAWSリージョン。
bucket任意S3のバケット。書いた場合は常にこちらを使います。
accountId任意12桁の数字を文字列で（クォートして）書きます。bucketを省くときだけ必要で、バケットはartifact-pages-<accountId>-<region>になります。認証情報から調べることはしません。
distributionId任意キャッシュの更新を依頼するCloudFrontのディストリビューション。書かなければ更新は依頼しません。

cloudflare：R2とCloudflareのキャッシュ

artifact-pages.yaml / CLOUDFLARE
provider: cloudflare
cloudflare:
  accountId: "<32文字のアカウントID>"
  zoneId: "<32文字のゾーンID>"
  publicBaseURL: https://docs.example.com
  # bucket は既定で artifact-pages、認証情報の変数名も既定のまま
キー意味
accountId必須R2のバケットを持つCloudflareのアカウント（16進数32文字）。
zoneId必須変更後にキャッシュを消すゾーン（16進数32文字）。
publicBaseURL必須読者が使う公開アドレス（HTTPS、パスなし）。キャッシュを消す依頼はこのアドレスで組み立てます。
bucket任意R2のバケット。既定はartifact-pages。
accessKeyIdEnv、secretAccessKeyEnv任意R2のアクセスキーを入れる環境変数の名前。既定はCF_R2_ACCESS_KEY_IDとCF_R2_SECRET_ACCESS_KEY。
apiTokenEnv任意キャッシュを消すときに使うAPIトークンの変数名。既定はCF_API_TOKEN。
sessionTokenEnv任意R2の認証情報が一時的なものの場合に、セッショントークンを入れる変数名。
registryReaderAccessKeyIdEnv、registryReaderSecretAccessKeyEnv、registryReaderSessionTokenEnv任意site syncとpreview publishが、サイトの登録情報を読むときだけに使う、読み取り専用の別の認証情報。最初の2つは組で設定します。認証情報を参照してください。

値はすべて仮のものです。バケット、ホスト名、キャッシュのルール、プレビューの保持期間は、このファイルではなくCloudflareやAWS側（Terraformなど）で設定します。なお、コマンドはgcp-localというプロバイダーも受け付けますが、これはテスト用のエミュレーター向けで、本番の配信先ではありません。

認証情報

設定ファイルには環境変数の名前だけを書き、認証情報の値は書きません。それぞれのジョブには、必要なものだけを渡します。

  • AWSは、AWSの標準の認証情報の探し方に従います。環境変数、プロファイル、CIで引き受けるロール（GitHub ActionsのOIDCなど）が使えます。
  • Cloudflareは、cloudflareブロックで名前を指定した環境変数を読みます。コマンドごとに必要なものは次のとおりです。
コマンドR2のアクセスキーとシークレット登録情報の読み取り用APIトークン
site sync必須設定したときだけ使うサイトを変える実行と、終わっていないキャッシュ削除をやり直す実行で必要。書き込む前に確認する
preview publish必須設定したときだけ使う不要
registry sync必須使わない登録情報を変える実行、一覧から外したサイトを片付ける実行で必要。書き込む前に確認する
app deploy必須使わないアプリを変える実行ではすべて必要。書き込む前に確認する
lock inspect、lock recover必須使わない不要
index build、config set-default不要使わない不要

APIトークンは、変わったURLのキャッシュ削除をCloudflareに依頼するために使います。内容を変える実行でトークンがないと、何も書き込まずに止まります。ドライランと、変更がない実行では、APIトークンはいりません。チームの公開ジョブに許可するのは、サイトの登録情報の読み取りと、そのサイトのファイルとキャッシュ再試行の記録（_control/sites/<site>/site-cache.json）の読み取り・書き込み・削除、プレビューとロックの読み取り・書き込み、それにCDNへのキャッシュ更新の依頼（AWSではCloudFrontの無効化、Cloudflareではゾーンのキャッシュ削除）だけです。登録情報や閲覧アプリへの書き込みは必要ありません。登録情報の読み取り用の項目を設定すると、登録情報はその別の認証情報で読むので、主な認証情報をそのサイトだけに絞れます。項目を設定したのに値がない場合は、主な認証情報で代用せずに、公開を止めます。

sites

sitesには、サイトIDごとに、中身をどこから公開するかを書きます。

項目決まり
サイトID（キー）必須英小文字と数字を、1つのハイフンでつなげたもの。checkoutやmobile-iosなど。URLに使われます。assetsは予約されていて使えません。
name必須表示名。空白や記号を含めてもよく、ほかのサイトと同じ名前でもかまいません。
description任意サイトの一覧と@のパレットで、サイト名に添えて表示する短い説明。
repository必須GitHubのowner/repoそのもの。URLや、末尾が.gitの値は使えません。大文字と小文字は区別せずに比べます。
sourcePath必須公開するディレクトリ。リポジトリのルートからの相対パスを/区切りで書き、ルートは.です。先頭の/、..、バックスラッシュは使えません。文字列のまま比べます。

同じリポジトリと同じディレクトリの組は、1つのサイトにしか登録できません。1つのリポジトリの別々のディレクトリから、複数のサイトを公開することはできます。ブランチの設定はなく、どのブランチから公開するかはチームのワークフローで決めます。

全件を書く

sitesには、あるべきサイトをすべて書きます。一覧から消えたサイトは次のregistry syncでdesired setから外れ、公開したページ、インデックス、プレビューが削除されます。必ずドライランの結果を確かめてください。

登録コマンドでsitesそのものを書かないとエラーになり、空の一覧としては扱われません。サイトを1つも置かないときはsites: {}と書きます。

sitesを読むのはregistry syncだけです。site syncとpreview publishは配信先にある登録情報を確認するので、チーム側の設定ファイルには配信先だけを書いておけば足ります。

サイトの変更を反映する

sitesを編集したら、管理リポジトリから反映します。まず--dry-runで計画を確かめます。

ターミナル / 管理者
# ファイルに合わせてサイトを追加・変更・削除する
$ artifact-pages registry sync --dry-run
$ artifact-pages registry sync
# 1つのサイトだけ外すとき：先に sites から消してから
$ artifact-pages registry sync --dry-run
$ artifact-pages registry sync
  • registry syncは、配信先の登録情報をsitesの全体に合わせ、一覧から消えたサイトの中身を片付けます。
  • サイトを1つ削除するには、ほかのサイトを残したままsitesから対象を外し、ドライランを確認してregistry syncを実行します。途中で止まっても、再実行で片付きます。
  • 削除した中身がしばらくキャッシュに残ることがあり、読者がすでに開いたページは取り消せません。
  • 止まった実行がロックを残したときは、lock inspect --scope registry（サイトのロックなら--site ID）で確認します。何も実行されていないことを確かめてから、確認したときの値をlock recover … --observed-etag ETAGに渡して解除します。

同じファイルは、閲覧アプリを置くapp deployでも配信先として使います。app deployが置くのは、使っているCLIと同じバージョンのアプリです。リリースはGitHub Releasesで確認できます。
