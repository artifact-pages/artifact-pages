公開は各チームで、読む場所はひとつに

各リポジトリから公開し、ひとつの場所で読む。

成果物はGitで作ってレビューし、チームごとに公開します。全サイトをまとめて組み立てるビルドはなく、各チームは自分のリポジトリとCIから、自分のサイトだけを公開します。公開したサイトは共通の静的な配信先に集まり、読者は1つの閲覧アプリでサイトを選び、ページを探して読み、リンクで共有できます。操作はどのサイトでも同じです。

読者は、サイドバーからページを選び、⌘K / Ctrl Kで検索し、@でサイトを切り替えます。JavaScriptを有効にすると、ここで動きを確認できます。

画面は、このガイド自身のページと説明用の例で構成した見本です。

01
Gitが正本

成果物は、それを作ったリポジトリでレビューし、Gitの履歴とともに公開します。Artifact Pagesの中で編集することはありません。HTMLとMarkdownはファイル名と拡張子のまま、/サイト/ファイル名.htmlのURLで開けます。

02
公開はサイトごとに独立

1つのGitリポジトリのディレクトリが、1つのサイトになります。各サイトは自分のリポジトリから、変更があったときに自分の範囲だけを公開し、ほかのサイトのビルドやデプロイを待ちません。

03
読む場所はひとつ

公開したサイトは共通の静的な配信先に集まり、常時動くサーバーを持たない静的な配信（オブジェクトストレージとCDN）から届きます。サイトの切り替え、ページの検索、目次、Gitへのリンクは、どのサイトでも同じ閲覧アプリで使えます。

読者向け

読むときにできること

どのチームのサイトも、同じ閲覧アプリと同じ操作で読めます。操作はブラウザの中で完結し、検索はいま開いているサイトの中で行います。見本のページは説明用の例です。

  • https://<配信ドメイン>/checkout/design/payment-flow.html
    checkout/design/決済フロー設計

    ページごとに変わらないURL

    URLは、サイトのIDと、公開元でのファイルのパス（拡張子まで）でできています。共有しても、ブックマークしても、再読み込みしても、同じページが開きます。

  • ⌕決済esc

    コマンドパレットが、入力に合わせてタイトルとパスから候補を絞ります。#で開いているページの見出しへ、>でコマンドへ。

    本文検索を有効にして公開したサイトだけで使えます。

しくみ

公開から閲覧までの流れ

Gitの文書が読者に届くまでには、4つの役割があります。管理者が用意するのは共通の閲覧アプリとサイトの登録で、公開は各チームのリポジトリがそれぞれ行います。ファイルの置き場所や、リクエストごとに動くサーバーがない理由など、内部のしくみは「アーキテクチャの全体像」で説明しています。

01 / アプリを配置 管理者

まず、読むためのアプリを置く。

管理者が、静的な閲覧アプリ（SPA）を配信先へ一度だけデプロイします。これがすべてのサイトに共通する入口です。アプリのWebリリースを取得して検証してから、アプリ本体のファイルだけを書き込みます。

ターミナル / 管理者
# まず変更計画だけ確認（何も書き込みません）
$ artifact-pages app deploy --dry-run
# 反映
$ artifact-pages app deploy

app deployは、使っているCLIと同じバージョン（x.y.z）の閲覧アプリを配置します。別のバージョンのアプリを置くときは、そのバージョンのCLIを使います。リリースはGitHub Releasesで確認できます。配信先の設定は--config、または管理リポジトリのartifact-pages.yamlから解決されます。サイトのインデックスや文書には触れません。

02 / サイトを登録 管理者

次に、サイトを登録する。

サイトは、チームごとに持つのが基本です。同じチームでも、プロダクトごとに分けてかまいません。サイトには、ID、表示名、元になるGitリポジトリ（owner/repo）とディレクトリ（sourcePath）があり、管理者が設定ファイルに書いて登録します。まだ文書がなくても登録できます。

artifact-pages.yaml / 管理リポジトリ
sites:
  sre:
    name: SREチーム
    repository: acme/sre-handbook
    sourcePath: docs/public
  checkout:
    name: 決済チーム / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts
  billing:
    name: 決済チーム / Billing
    repository: acme/billing
    sourcePath: docs/artifacts
ターミナル / 管理者
$ artifact-pages registry register --dry-run
$ artifact-pages registry register

sitesに書いたサイトが、登録するサイトのすべてです。ここから外したサイトは、次のregistry registerで登録解除され、公開済みの内容も削除されます。配信先（provider）の設定は省略しています。

03 / Gitから公開 各チームのリポジトリ

各Gitリポジトリから、担当サイトへ公開する。

各チームのGitリポジトリが、担当するサイトと公開するディレクトリを明示して公開します。公開のたびにインデックスを作り、HTMLとMarkdown、CSSや画像をそのまま配置します。

公開はサイトごとに独立しています。全サイトをまとめて組み立てるビルドはなく、各リポジトリは自分のCIから、変更があったときに自分のサイトだけを公開します。ほかのサイトの公開を待つこともありません。

ターミナル / acme/checkout
# docs/artifacts を、サイト checkout へ
$ artifact-pages site publish --site checkout --source docs/artifacts --dry-run
$ artifact-pages site publish --site checkout --source docs/artifacts

書き込む前に、いまのリポジトリとディレクトリが、配信先に登録された内容と一致するかを確認します。他のサイトには書き込みません。マージ時にCIから同じコマンドを実行する運用を想定しています。

04 / 開いて探す 読者

あとは、URLを開けば読める。

読むのに必要なのはブラウザだけです。読んでいる途中でも⌘K / Ctrl Kで、いまのサイトのページと、開いているページの見出しを探せます。@を打つと、ほかのチームのサイトへ切り替えられます。

URLはファイル名と拡張子を保持するので、文書へのリンクをそのまま共有できます。<配信ドメイン>は、管理者が配信先に選んだアドレスです。画面の見方や検索の使い方は「読者の体験」にまとめています。

Git → Web / いま見えている構成01 / 04
共通の閲覧アプリが、みんなの読む場所になります。チームやプロダクトごとに、公開先のサイトを登録します。各リポジトリが、それぞれのタイミングで担当のサイトだけを公開します。全体をまとめるビルドはありません。読者はURLを開き、検索して、次の文書へ進みます。

使用例

チームのサイトを開くと、こう見えます。

決済チームのcheckoutサイトのトップページです（説明用の例）。⌘Kのあと@で、ほかのチームのサイトへ移れます。

サイトを移るときは、⌘K / Ctrl Kを押してから@を入力します。チームやプロダクトごとのサイトが並び、選ぶとそのサイトのトップページが開きます。
