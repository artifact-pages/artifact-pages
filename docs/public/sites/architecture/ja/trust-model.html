信頼モデル

要点公開することが、信頼するという判断です。公開したHTMLは承認済みの実行可能なコンテンツとして、アプリと同じオリジンの、サンドボックスの無いiframeで表示します。Markdownはサニタイズし、スクリプトは決して動かしません。誰が読めるかは運用者のエッジやネットワークが決め、Artifact Pagesは決めません。

公開することが信頼の判断

Git Artifact Pagesは、HTMLのレポート、ダッシュボード、図を、スクリプトも含めて作者が作ったとおりに見せるためのものです。そのため、公開したHTMLを承認済みの実行可能なコンテンツとして扱います。チームが自分たちの社内ページを信頼するのと同じです。誰が公開できるか（人、CIのワークフロー、認証情報）は運用者が決めます。製品は、悪意のあるHTMLを安全に見せようとはしません。

1つの組織、または互いに信頼し合ういくつかのチームが1つのオリジンに公開する使い方に合わせた、意図的な設計です。互いに信頼できない公開者が同居する使い方は想定していません。

HTML：同一オリジン、サンドボックスなし

閲覧アプリは、/_artifacts/<site>/<path>を、アプリと同じオリジンから、sandbox属性の無い普通のiframeに読み込みます。こうすると、相対URL、ESモジュール、フォント、fetchが、ファイルを直接開いたときと同じように動き、成果物のCSSがアプリに漏れることもありません。

その結果として、仕様にも書いているとおり、成果物のスクリプトは親のアプリのDOM、ローカルの保存領域、同じオリジンのほかのコンテンツにアクセスできます。閲覧アプリはピン留め、最近読んだページ、テーマをローカルの保存領域に置いているので、成果物がそれを読んだり書き換えたりすることもできます。このドキュメントのページはこの性質を意図して使っています。ページのスクリプトが親のページから閲覧アプリのテーマを読んで合わせ、逆に閲覧アプリは本文検索の語を強調するためにフレームの中へ手を伸ばします。

サイトごとのContent Security Policy

エッジは、成果物の応答ごとに強制のCSPを付けます。ローカルではnginxがリクエストのパスから組み立てます。

Content-Security-Policy · /_artifacts/checkout/…
default-src http://localhost:4179/_artifacts/checkout/ https: data: blob:;
script-src  http://localhost:4179/_artifacts/checkout/ https: 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval' data: blob:;
style-src   http://localhost:4179/_artifacts/checkout/ https: 'unsafe-inline' data: blob:
  • 許可するもの：ページ自身のサイトのパスの下にあるリソースと、あらゆるHTTPSのオリジン（CSS、スクリプト、画像、フォント、メディア、fetch）。通常のTLS、CORS、混在コンテンツの規則には従います。成果物は信頼されているので、インラインのスクリプトとスタイル、evalも許可します。
  • 拒否するもの：安全でない外部のhttp:のリソース。
  • サイトの間の壁ではありません。https:はすべてのHTTPSのURLに一致するので、アプリをHTTPSで配信すると、同じオリジンにあるほかのサイトのパスにも一致します。つまり本番では、あるサイトのページがほかのサイトのファイルを読み込めます。ローカルの素のHTTPでは、パスの指定がほかのサイトのパスを拒否します。すべてのサイトが1つのオリジンを共有するので、'self'はあえて使っていません。許可したHTTPSのリソースが、ほかのHTTPSのURLへリダイレクトすることもあります。

実際の帰結として、共有のファイルはサイトごとに複製を持ちます。たとえばこのドキュメントのサイトは、同じsite.cssとsite.jsをサイトごとのassets/に置き、ほかのサイトから読み込みません。ローカルと本番のどちらのポリシーでも動くようにするためです。

Markdown：サニタイズし、実行しない

Markdownは別のモデルです。アプリは、埋め込まれた生のHTMLをサニタイザーに通し、スクリプトを含む要素や許可しない要素・属性を取り除いてから、自分のDOMに描画します。Markdownを公開しても、スクリプトを実行する許可にはなりません。

  • Mermaidの図は、securityLevel: "strict"で図の操作を無効にしてローカルで描画します。描画に失敗したら、元のテキストをコードとして表示したままにします。
  • 相対パスのリソースはMarkdownのファイルの位置から解決し、そのサイトの成果物の名前空間の中に限ります。外部のリンクと画像はHTTPSに限ります。data:はbase64のPNG、JPEG、GIF、WebP、AVIFの画像だけ、mailto:のリンクは許可します。
  • 同じサイトのページへのリンクはアプリのルートになり、それ以外のリンクはnoopenerとnoreferrerを付けて新しいタブで開きます。

プレビューも同じ信頼で扱う

プレビューのHTMLも、本番とまったく同じモデルで表示します。同じオリジン、サンドボックスの無いiframe、リビジョンのパスに合わせた同じリソースの規則です。preview publishを実行することは、マージ前のその内容を承認することで、どんな変更でも安全に見られるビューアーではありません。だから信頼の確認は入口にあります。

  • プレビューするのは、サイトの登録済みリポジトリにあるheadだけです。フォークからのプルリクエストは、登録済みのリポジトリが宛先でも対象外です。
  • 特権のあるpull_request_targetのワークフローで、フォークの内容をチェックアウトして実行してはいけません。
  • プレビュー専用のホスト名、srcdocによる代替表示、一律のAccess-Control-Allow-Origin: nullやワイルドカードのCORSは使いません。

フォークのプレビューや、互いに信頼できない公開者に対応するには、別のオリジンなど、承認と隔離の別のモデルが必要です。それは製品としての新しい判断になります。

誰が読めるかはエッジで決める

Artifact Pagesには、読者のアカウント、ログイン、セッション、役割、サイトごとのアクセス方針がありません。中身を制限する必要があれば、運用者が配信のエッジや周りのネットワークで設定します。VPNやIPの制限、Basic認証、IDプロバイダーとCloudFrontの署名付きCookie、Cloudflare Accessなどです。リクエストが通れば、誰にでも同じ静的な中身を返します。

読者の身元を製品に入れない理由は次のとおりです。

  • 製品が静的なままでいられる。確かめるセッションが無いので、どのCDNでもすべてのオブジェクトをキャッシュして配信でき、身元ごとにキャッシュを分けて間違える心配もありません。
  • 仕組みは運用者が選べる。組織ごとに、使っているプロバイダーやIDの仕組みに合う関門を選び、ホスト名、一部のパス、ネットワーク全体のどれを守るかも決められます。製品がIDの方針を定める必要はありません。
  • 1つの境界ですべてを覆える。オリジンの前に関門を1つ置けば、ページ、インデックス、検索データ、プレビューをまとめて守れます。

そのためには、関門が論理ルートと生の/_indexes/*、/_artifacts/*、/_previews/*を覆い、守るべき中身がオリジンや共有キャッシュから返る前に働く必要があります。次のものは、はっきりとアクセス制御ではありません。

  • サイトの登録情報からサイトを外すこと、画面の一覧から隠すこと。オブジェクトを消すまでは、直接のURLで開けます。
  • 推測しにくいプレビューのSHA、プレビューが「マージ前」であること。
  • 登録解除を取り消しとみなすこと。オリジンのオブジェクトを消してキャッシュの無効化を依頼しますが、すでに届いた中身は取り戻せません。

公開者の認証情報と制御用のオブジェクト

サイトの登録情報の確認とサイトのロックはArtifact Pagesのコマンド同士の調整で、権限の仕組みではありません。バケットへ直接書き込める認証情報を持つ人は迂回できます。公開者が触れる範囲を絞るのは、プロバイダーの認証情報の役目です。別のリポジトリから公開する人に許すのは、サイトの登録情報のオブジェクトの読み取り、自分のサイトのインデックスと成果物の接頭辞の中での読み書きと削除、プレビューの接頭辞の読み書き（AWSの参照構成では、プレビューの履歴を消す権限は与えません）、サイトのロック_control/sites/<site>/lock.jsonの読み書き、キャッシュ再試行の記録_control/sites/<site>/site-cache.jsonの読み書きと削除、それにCDNの無効化の依頼（CloudFrontのCreateInvalidation、またはキャッシュ削除の権限を持つCloudflareのゾーンのトークン）です。無効化の依頼が要るのは、中身が変わる公開が、変わったURLのキャッシュを消すからです。サイトの登録情報とアプリケーションプレーンへの書き込みは許しません。Cloudflareでは、サイトの登録情報を読むための別の身元を任意で設定できます。AWSの参照構成では、管理者用と公開者用に分けたロールをGitHub ActionsのOIDCで使う想定です。

/_control/*にある非公開の調整用オブジェクトは、読者に返してはいけません。ロックや再試行の記録の中身を返さない限り、配信側がこれらのパスにアプリのシェルを返すことは許されます。

どこまで実証されているか

  • ローカルで実証済みiframeでのCSSの閉じ込め、害の無いフィクスチャからの意図どおりの親のDOMと保存領域へのアクセス、Markdownからのスクリプトの除去、nullやワイルドカードのCORSを付けない同一オリジンでのモジュールの読み込み、CSPによる外部HTTPSの許可と外部HTTPの拒否（T4、T6、ISSUE-037のブラウザのテスト）。
  • Cloudflareで抜き取り確認2026-10-01に、稼働中のGuideのHTMLに強制の成果物CSPのヘッダーが付くこと、プレビューのHTMLにリビジョンのパスに合わせた強制のCSPが付くこと、制御用のキーのパスがアプリのシェルしか返さないことを確かめました。2026-10-02には、稼働中のGuideのページで実行時に組み立てたHTTPのURLへのfetchが、強制のCSP（default-srcから引き継ぐconnect-src）で拒否されること（Chromium）、範囲を絞った一時的なR2の認証情報が自分のサイトの外への書き込みを拒否されつつ、そのサイトは公開できることを確かめました（T15）。
  • 未実証リソースの種類とブラウザをひととおり組み合わせた、外部HTTPの拒否の確認。公開者のプロセスからキャッシュ削除用のトークンを切り離すこと。GitHubのOIDCのロール、AWSでの実際の動作すべて。
