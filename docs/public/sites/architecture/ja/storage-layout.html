ストレージの構成

要点読者が目にするものは、すべて決まったキーにある静的なオブジェクトです。サイトの登録情報（レジストリ、sites.json）が1つ、サイトごとに小さなJSONが2つ、サイト専用の接頭辞の下にファイル一式、必要に応じて検索とプレビューのオブジェクト。オブジェクトの種類ごとにキャッシュの規則が決まっています。

サイトの登録情報：sites.json

サイトの一覧は、管理者がartifact-pages.yamlのsitesに書き、Gitでレビューします。registry syncがそれを検証して/_indexes/sites.jsonを書きます。中身はサイトIDで並べた配列なので、同じ内容のYAMLからは常に同じJSONができます。JSONを手で編集することはありません。

/_indexes/sites.json
{
  "schemaVersion": 1,
  "sites": [
    {
      "id": "checkout",
      "name": "Payments / Checkout",
      "description": "Payment flow designs and incident reviews.",
      "repository": "acme/checkout",
      "sourcePath": "docs/artifacts"
    }
  ]
}

このファイルには読み手が2つあります。ブラウザはID、名前、説明を使ってサイトを並べます。公開コマンドはrepositoryとsourcePathを使い、公開しようとしているチェックアウトが登録どおりのソースかを確かめます。このファイルが変わるのはサイトの登録とregistry syncによるサイト削除のときだけで、公開では変わりません。値は説明用の例です。

サイトごとの2つの文書：meta.jsonとindex.json

サイトごとに、小さな発見用の文書と、成果物をすべて載せたインデックスがあります。役割は分かれています。

meta.json：小さい。全サイト分を読む

サイトのタイトルと説明、artifactCount、generatedAt、インデックスの場所を示すartifactIndexUrl、本文検索を公開した場合のfullTextUrl。成果物ごとの記録は持ちません。

index.json：全件。開いているサイトの分だけ読む

HTMLとMarkdownの文書ごとに1件。idとpath（ソースからの相対パスそのまま）、title、format、artifactUrl、updatedAt、lastCommitter.name、source（リポジトリ、URL、ref、ファイルのパス）、目次の見出しtoc。

/_indexes/checkout/meta.json
{
  "schemaVersion": 1,
  "site": {
    "id": "checkout",
    "title": "Payments / Checkout",
    "description": "Payment flow designs and incident reviews."
  },
  "generatedAt": "2026-09-28T00:00:00Z",
  "artifactCount": 4,
  "artifactIndexUrl": "/_indexes/checkout/index.json",
  "fullTextUrl": "/_indexes/checkout/search/manifest.json"
}

場所を指すフィールドがあるので、ブラウザは場所を決め打ちせずに済みます。文書が1つもないサイトも公開できます。その場合インデックスは"artifacts": []、メタデータは"artifactCount": 0になり、閲覧アプリは未公開ではなく空のサイトとして表示します。

  • meta.jsonが404なら、登録済みのサイトを「まだ公開されていない」として一覧に残します。それ以外のエラーなら、詳細を表示できない状態で一覧に残します。1つのサイトの不具合で一覧全体が壊れることはありません。
  • 表示用のタイトルは、HTMLなら<title>、Markdownなら最初のH1から取り、無ければファイル名を読みやすくして使います。updatedAtとコミッターはGitの履歴から取ります。履歴の無いファイルは更新日時にファイルの変更時刻を使い、コミッターは記録しません。

ブラウザが読み込むものと、そのタイミング

リクエストの数は、サイトの数ではなく読者の操作に応じて増えます。インデックスの全体をダウンロードするのは、開いているサイトの分だけです。

ブラウザはストレージの一覧を取りません。オブジェクトストレージの一覧APIを呼ばず、nginxのautoindexにも頼りません。探す必要のあるものは、すべてsites.json、meta.json、index.jsonに名前が書いてあります。

成果物のキーとルート

sourcePathがdocs/artifactsのサイトにあるdocs/artifacts/design/flow.htmlは、/_artifacts/checkout/design/flow.htmlに保存され、/checkout/design/flow.htmlで開きます。ディレクトリの構成も名前もそのまま保つので、ページとCSS、スクリプト、画像、モジュールの間の相対リンクはそのまま動きます。

  • .html、.htm、.mdはすべてページになります。index.htmlも、_includes/のようなフォルダにあるファイルも同じです。それ以外のファイルはコピーされ、URLで参照できますが、ページとしては一覧に出ません。
  • パスの区切りごとに1回だけパーセントエンコードします。artifactUrlやルートを作るときの規則です。空白、#、?、%、+、日本語の名前も往復で崩れません。UTF-8として正しくないファイル名は拒否します。
  • リソースは相対パスで参照します。/assets/report.cssのようなルート相対のURLはオリジンの先頭から始まり、サイトの名前空間の外に出てしまいます。
  • 存在しないリソースには実際の404応答を返し、アプリのシェルは返しません。

保存するオブジェクトのContent-Typeは、公開するマシンのMIMEデータベースではなく、大文字小文字を区別しない固定の拡張子表で決めます。Content-Disposition: attachmentは付けず、実際に圧縮していないのにContent-Encodingを名乗ることもしません。

拡張子Content-Type
.html、.htmtext/html; charset=utf-8
.md、.markdowntext/markdown; charset=utf-8
.css / .js、.mjs、.cjstext/css; charset=utf-8 / text/javascript; charset=utf-8
.json、.mapapplication/json; charset=utf-8
.svgimage/svg+xml; charset=utf-8
画像、フォント、.pdf、.wasmそれぞれの標準の型（例：image/png、font/woff2、application/wasm）
それ以外application/octet-stream（コピーされ、URLで参照できます）

キャッシュの規則と理由

2つのプレーンは変わる頻度が違うので、規則も分けています。変わりうるURLはブラウザが毎回再検証し、共有キャッシュには短く上限のある期間だけ保持させます。内容が変わると名前も変わるURLは、1年キャッシュします。

オブジェクトCache-Control
/index.html、名前が固定のアプリのファイルno-cache, max-age=0, must-revalidate
/assets/<name>-<8文字のハッシュ>.*public, max-age=31536000, immutable
sites.json、meta.json、index.json、search/manifest.jsonpublic, max-age=0, s-maxage=60, must-revalidate
/_artifacts/<site>/*public, max-age=0, s-maxage=300, must-revalidate
search/root-*.gz、search/leaf-*.gzpublic, max-age=31536000, immutable
プレビューのcatalog.json /リビジョンのファイルs-maxage=60 / s-maxage=300（どちらもmax-age=0, must-revalidate）

上限のある鮮度は、あくまで最後の守りです。site syncはオリジンを更新したあと、変わったURLだけをCDNに無効化させ、その依頼が成功するまで再試行の記録を残します（公開の仕組みを参照）。依頼が成功しても、すべてのエッジが更新済みとは限らず、すでにページを開いている読者の画面も更新されません。

ローカルのnginxは、開発中の変更がすぐ見えるように/_indexes/*をno-storeで返します。上の表は、公開時に各オブジェクトへ保存する値と、プロバイダーの配信が守るべき値です。稼働中のCloudflareでは、抜き取ったインデックスと成果物の応答がこの値と一致しました（T15）。AWSの実際のヘッダーはまだ確認していません。

非公開の制御領域

調整のための状態は、どのサイトのインデックスや成果物の接頭辞にも入らない/_control/に置きます。サイトを片付けても消えません。

キー用途
_control/locks/sites/<site>.jsonサイトの公開、プレビューの公開、registry syncによるサイト削除が共有するサイトごとのロック。registry syncによるサイト削除のあとも（freeの状態で）残します。
_control/locks/registry.jsonサイトの登録情報の更新を1つずつ順に行うためのロック。
_control/site-cache/<site>.json失敗した公開のあと、まだ済んでいないキャッシュ無効化のパス。
_control/registry-cleanup.jsonサイトの登録情報から外したサイトについて、まだ済んでいない片付け。

配信では、これらの中身を決して返しません。ローカルのnginxは/_control/*に404を返します。プロバイダーによっては代わりにアプリのシェル（「Page not found」を表示）を返すこともあります。
