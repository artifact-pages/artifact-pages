Git Artifact Pagesの仕組み

要点正本はGitにあります。各サイトは自分のリポジトリから、ほかのサイトとは別々に公開し、その結果はオブジェクトストレージにある共通の静的な投影に集まります。ブラウザ上の1つの静的な閲覧アプリがその投影を読み、どのサイトも同じように表示します。リクエストの経路にアプリケーションサーバーはありません。

Gitが正本、Webサイトはそこから作る投影

成果物は、それを作るリポジトリで作成とレビューを行い、Artifact Pagesが書き換えることはありません。サイトは、リポジトリとソースディレクトリの組（repositoryとsourcePath）として1つずつ登録します。公開コマンドはGitのチェックアウトからそのディレクトリを読み、サイトのインデックスを作り、ファイルをそのままコピーします。テンプレートの展開、CSSやJavaScriptのバンドル、リンクの書き換えは行いません。

ブラウザに届くものはすべて、Gitから作り直せる投影です。閲覧アプリもオブジェクトストレージもCDNも、正本ではありません。公開したオブジェクトが消えても、公開が途中で止まっても、同じソースをもう一度公開すれば同じ状態に戻ります。収束の仕組みは公開の仕組みで説明します。

公開はサイトごとに、読む体験は共通に

公開には、全サイトをまとめる段階がありません。管理者は閲覧アプリをデプロイし、artifact-pages.yamlのsitesに各サイトを1度登録します。どちらの操作も、サイトの中身はビルドしません。そのあとは各サイトのリポジトリが、内容が変わったときに自分のCIからsite publishを実行します。1回の公開が書き込むのはそのサイトの/_indexes/<site>/と/_artifacts/<site>/だけです。サイトごとのロックの下で動くので、ほかのサイトを作り直すことも、ほかのサイトを待つこともありません。

誰がコマンド書き込む先いつ
管理者app deployアプリケーションプレーン閲覧アプリを更新・切り戻すとき
管理者registry register/_indexes/sites.json登録するサイトが変わったとき
各サイトのリポジトリsite publishそのサイトの/_indexes/<site>/と/_artifacts/<site>/そのサイトの内容が変わったとき。タイミングは各サイトで決める

サイトどうしが共有するのは、静的な投影の構成と、それを読む閲覧アプリです。どのサイトの出力も同じオブジェクトの構成に従い、アプリは/_indexes/sites.jsonと各サイトの小さなmeta.jsonからサイトを見つけます。そのため、別々に公開したサイトがばらばらのWebサイトにならず、1つのArtifact Pagesとしてまとまって見えます。サイトの選択、ファイルツリー、コマンドパレット、本文検索（有効にして公開したサイトのみ）、ピン留めと最近読んだページ、成果物の表示、目次と詳細、プレビューとGitへのリンクは、どのサイトでも同じように使えます。検索は、いま読んでいるサイトの中で行います。

2つのプレーンと非公開の領域

オリジンの中身は、変わる頻度で分けています。アプリケーションプレーンは閲覧アプリで、運用者が更新したときだけ変わります。コンテンツプレーンは公開されたサイトで、誰かが公開するたびに変わります。2つは別々にデプロイします。アプリを更新してもサイトのオブジェクトには触れず、サイトを公開してもアプリには触れません。

領域パス変わるとき書き込むコマンド
アプリケーションプレーン/index.html、/assets/*（ほかに/preview-bridge.js、/LICENSE、/THIRD_PARTY_NOTICES.txt）閲覧アプリの更新・切り戻しapp deploy
コンテンツプレーン/_indexes/*、/_artifacts/*、/_previews/*サイトの登録・公開・プレビュー・登録解除registry register / unregister、site publish、preview publish
制御（非公開）/_control/*コマンドがロックを取る、再試行の記録を残す上と同じコマンド。配信はしない

オブジェクトのキーとキャッシュの規則はストレージの構成にまとめています。

論理ルートとストレージのパス

読者が使い、共有するURLは3種類だけです。ストレージのパスは内部の都合で、画面移動のURLには使いません。

ルート表示するもの例（説明用）
/サイトの選択/
/:siteサイトのホーム/checkout
/:site/*1つの文書/checkout/design/flow.html

/checkout/design/flow.htmlを開くと、エッジはアプリのシェルを返します。アプリは/_indexes/sites.jsonと各サイトの小さなmeta.jsonを読み、checkoutが開いているサイトになったので/_indexes/checkout/index.jsonを読み込み、最後に/_artifacts/checkout/design/flow.htmlをiframeに読み込みます。

  • ファイル名と拡張子はルートに残ります。flow.htmlとflow.mdは別のページです。index.htmlも名前を指定して開くもので、フォルダのURLで暗黙に開くことはありません。
  • パスの区切りごとに1回だけパーセントエンコードします。空白、#、?、%、日本語の名前も意味を保ちます。名前をslug化することはありません。
  • サイトは論理的な名前空間で、リポジトリではありません。リポジトリはメタデータとして記録し（詳細パネルに表示）、URLには出しません。サイトを別のリポジトリへ移しても、リンクは変わりません。

エッジの役割

配信側に必要なのは、パスによる振り分けだけです。オブジェクトのパスはストレージへ、それ以外はアプリのシェルへ送ります。

リクエスト返すもの
/_indexes/*、/_artifacts/*、/_previews/*、/assets/*保存済みのオブジェクト。存在しなければ実際の404応答を返し、アプリのシェルは返しません。成果物の相対リンクが壊れていれば、目に見えて失敗します。
/_control/*制御オブジェクトは決して返しません。アプリのシェル（「Page not found」を表示）を返すことはありますが、ロックや再試行の記録の中身は返しません。
それ以外アプリのシェル/index.html。論理ルートはブラウザ側で解決します。

ローカルではDocker Compose上のnginx（docker/nginx/default.conf）がこれを担います。AWSの参照構成では、Origin Access Controlで非公開のS3バケットを読むCloudFrontが担います。Cloudflareの構成では、カスタムドメインのR2の前にCache/CDNを置き、論理ルートを/index.htmlに書き換えるTransform Rulesを使います。

リクエスト時のサーバーを持たない理由

設計の原則は静的を基本にし、リクエスト時より公開時に計算することです。公開時に計算できるものは、そのときに計算してファイルとして置きます。

  • タイトル、パス、目次用の見出し、最終更新日時とコミッターは、ソースとGitの履歴から取り出してindex.jsonに書きます。
  • サイトの一覧は、管理者の設定から生成したJSONファイルで、ディレクトリの一覧ではありません。ブラウザはストレージの一覧APIを呼ばず、nginxのautoindexにも頼りません。
  • 本文検索を有効にした場合も、公開時に作る静的なファイル群です。検索とインデックスで説明します。

その結果、CDNのある静的ホスティングならどこでも配信でき、負荷への対応はCDNに任せられます。運用するデータベースも、サーバーサイドレンダリングも、検索APIもありません。代わりに、変更は公開してキャッシュが更新されるまで見えず、読者ごとの処理もできません。誰が読めるかはエッジで決めます。詳しくは信頼モデルを参照してください。

どこまで実証されているか

リポジトリはいま、ローカルで製品を固める段階にあります。上の契約はまずローカルで実証し、プロバイダーでの配信は別に確認しています。プロバイダーの確認はまだ終わっていません。

  • ローカルで実証済み閲覧アプリ、nginxによる振り分け、コミット済みのフィクスチャ、ローカルのストレージディレクトリへの登録済みサイトの公開。エミュレーターのプロファイル（S3 APIの形を確かめるMinIO、gcp-local用のfake-gcs-server）はアダプターとHTTPの契約を確かめるもので、実際のCloudFront、Cloudflare、GCPと同じ動きをする保証ではありません。
  • Cloudflareで抜き取り確認2026-10-01と10-02に、稼働中のCloudflare環境で、論理ルートがアプリのシェルを返すこと、存在しないオブジェクトが実際の404応答になること、キャッシュのヘッダーと、本番とプレビューのCSPヘッダーを確認しました。使い捨てのサイトでの公開、プレビュー、登録解除、プレビューの同時公開と中断からの復旧、範囲を絞った認証情報での公開、CSPによる実行時のHTTPの拒否も試しています。いずれも抜き取りで、プロバイダー配信の検証（T15）は継続中です。
  • 未実証AWS（CloudFrontとS3）での実配信、プレビューのライフサイクルで実際に削除されるまでの時間、プロバイダー上で別々のサイトを同時に公開する場合などの競合と復旧のケース、GitHubのOIDC。各ページの最後に、そのページに関わる未実証の項目を挙げています。
