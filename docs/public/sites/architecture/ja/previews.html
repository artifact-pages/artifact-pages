プレビューの仕組み

要点プレビューは、あるGitのheadで変更された文書を、コミットSHAで識別する不変のリビジョンとして公開し、サイトごとの小さなプレビューの一覧（catalog.json）に載せます。いつまで残すかはストレージのプロバイダーに任せます。リビジョンが消えたら、そのあとの本番の公開がプレビューの一覧から項目を除きます。

プレビューの対象

プレビューが答えるのは「変更したページがどう見えるか」で、「マージしたあとのサイト全体がどう見えるか」ではありません。

  • 選び方：デフォルトブランチのいまのHEAD（--default-ref、既定はorigin/HEAD）とプレビューするhead（--head、既定はHEAD）のマージベースを、そのheadと比べます。対象は、登録したソースパスの下で追加・変更されたHTMLとMarkdownだけです。名前を変えた文書は新しいパスでプレビューし、削除した文書にはプレビューがありません。
  • スナップショット：プレビューする中身は、すべてheadのコミット済みのツリーから取ります。デフォルトブランチとの仮のマージは作りません。
  • 結果：文書を削除しただけの変更はno-previewを返します。文書以外のファイルだけの変更はエラーです。
  • リソース：変更された文書に必要なローカルのCSS、JavaScript（静的なモジュールのimportは先までたどる）、画像、フォントを、相対的な配置を保ってリビジョンにコピーします。実行時に名前を組み立てるものは--include PATH（パスそのもの、またはpath.Matchのパターン）で加えます。JavaScriptが組み立てるルート相対のURLや、実行時の任意の画面移動は保証の対象外です。

記録、キー、ルート

オブジェクトキー中身
リビジョンのファイル/_previews/<site>/revisions/<sha>/files/<path>headのツリーにある文書とリソースを、バイト単位でそのまま
リビジョンのマニフェスト/_previews/<site>/revisions/<sha>/manifest.jsonheadSha、defaultHeadSha、mergeBaseSha、createdAt、bundleDigest、files[]（パス、SHA-256、Content-Type）、documents[]
プレビューの一覧/_previews/<site>/catalog.jsongroups[]：id（pr:<番号>またはhead:<sha>）、kind、headSha、任意のprUrl、updatedAt、documents[]

文書の論理ルートは/:site/_previews/<SHA全体>/<文書のパス>で、/:site/_previewsがそのサイトのプレビューの一覧です。任意で付ける?group=pr%3A42は閲覧アプリのための文脈で、リビジョンも中身も変えません。

リビジョンとグループ

2つの識別子は、役割が違います。

リビジョン＝headのSHA全体

プロバイダーに残っている間、リビジョンのURLが指す中身は変わりません。同じheadをもう一度公開すると、保存済みのオブジェクトを書き直さずに確かめます。同じheadで投影が違えばエラーです。直接のURLはプレビューの一覧ではなく、そのリビジョン自身のマニフェストで解決します。

グループ＝プレビューの一覧に何を出すか

プレビューの一覧には、グループごとに完了した最新のリビジョンを出します。--pull-requestを指定すればグループはpr:<番号>、指定しなければ手動のプレビューで、グループはhead:<sha>です。古いリビジョンはプレビューの一覧から外れますが、オブジェクトがある間は直接のURLで開けます。

PRとの関係を、ブランチ、コミット、CIのイベントから推測することはありません。--pull-requestを指定すると、CLIはGitHubのAPIでプルリクエストを読み、ベースのリポジトリ、headが同じリポジトリにあること、headのSHAを確かめます。フォークからのプルリクエストは対象外です。閲覧アプリはヘッダーに短いSHAを控えめに表示し、指定されたグループがいまもそのSHAを指しているとプレビューの一覧で確認できたときだけPRへのリンクを出します。

公開の順序とリンク

preview publishは、site publishやregistry unregisterと同じサイトのロックを取り、デプロイ済みのサイトの登録情報を確かめ直します。リビジョンのファイルとマニフェストは新規作成だけを許すオブジェクトとして書き、そのあとでプレビューの一覧を読み、グループ単位の冪等な追加・更新を行います。プレビューの一覧の更新に失敗したら失敗を報告し、再試行できます。プレビューの一覧に載らなかったオブジェクトも、ほかと同じくプロバイダーの保持期間で消えます。

プレビューの中で、ほかの変更された文書へのリンクは同じリビジョンのその文書を開きます。変更されていない文書へのリンクは本番のルートを開きます。HTMLのリンクはフレームの中にアプリを入れ子にせず、閲覧アプリそのものを移動させます。

プレビューは本番の画面には出ません。index.json、Browse、最近の更新、本文検索、パレットのページの候補のどれにも入りません。サイトのホームにはプレビューの一覧への控えめなリンクがあり、パレットには「Open previews」のコマンドがあります。プレビューの一覧を開いたときに読むのは、そのサイトのcatalog.jsonだけです。

保持期間と片付け

プレビューをいつまで残すかはプロバイダーが決めます。管理者はインフラの設定（CLIの設定ではありません）でpreview_retention_daysを1つ決めます。この値は、AWSならS3のライフサイクルによる期限切れ、CloudflareならR2のオブジェクトのライフサイクル規則になり、_previews/の接頭辞全体にかかります。アプリは期限の時刻を記録せず、タイマーも動かさず、正確な削除時刻も約束しません。

プロバイダーの削除は非同期なので、期限切れになったリビジョンをプレビューの一覧がしばらく指していることがあります。これには2つの仕組みで対処します。

  1. プレビューの一覧を開くと、閲覧アプリが候補ごとにマニフェストを確かめ、無いものを隠します。無いプレビューの文書には「Preview unavailable」とサイトへ戻る手段を表示し、無い生のリソースには実際の404応答を返します。
  2. site publishとpreview publishは毎回、サイトのロックの中でオリジンのプレビューの一覧を読みます。参照を除くのは、マニフェストが無いと確認できたときだけで、読み取りのエラーは無いことの証拠にしません。site publishが小さくなったプレビューの一覧を書くのは本番の投影を書き終えたあとなので、本番の公開が失敗してプレビューが隠れることはありません。

PRを閉じたときに動くワークフローはありません。マージ済み、閉じたもの、手動のプレビューも、マニフェストがある間はプレビューの一覧に出ます。registry unregisterは、サイトのほかの投影と一緒にプレビューもすぐに消します。

どこまで実証されているか

  • ローカルで実証済み記録の契約、直接のルート、エンコードされたパス、同じheadの再試行、マニフェストが消えた場合（T1）。消えたマニフェストを隠すことと生の404（T4）。グループの同時更新、中断した公開、プレビューと登録解除の両方の順序（T5）。リソース、先までたどるモジュール、変更・未変更の文書へのリンクの振り分け（T6）。ローカルのCLIで、無いと確認できた参照だけを除くこと（T8）。実際のCLI、ローカルのエッジとストレージのAPIで、リビジョンを1つ消したあとの本番の公開がその参照だけを除き、開いていたブラウザのプレビューの一覧から消え、古いURLが「Preview unavailable」になること（T17、npm run test:preview-retirement）。
  • Cloudflareで抜き取り確認2026-10-01に、使い捨てのサイトで、手動のプレビューがモジュールとリソースごと表示されること、同じheadの再試行がno-opになること、わざと消したマニフェストが次の本番の公開でプレビューの一覧から除かれること、R2がプレビューのオブジェクトにライフサイクル規則を示すことを確かめました。2026-10-02には、CLIで新しい2つのheadを同時に公開して両方がプレビューの一覧に残ること、途中で止めた公開のロックを観測したETagで復旧して再試行できること、ロックを失った古いプロセスがプレビューの一覧を書き換える前に拒否されることを確かめました。リビジョンを1つ消したあとの本番の公開ではその参照だけが除かれ、ブラウザのプレビューの一覧からも消えました（古いURLは再読み込みで「Preview unavailable」になりましたが、すぐに消えるわけではありません）（T15）。
  • 未実証プロバイダーのライフサイクルで実際に削除されるまでの時間（観察中）、実際のGitHubのプルリクエストとCIからの公開、AWSに対する片付け。
