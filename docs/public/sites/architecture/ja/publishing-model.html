公開の仕組み

要点site syncは、保存されたサイトを1つのソースディレクトリと同じ状態にします。あるべき投影の全体とオリジンにあるものを比べ、参照が壊れにくい順に差分を書き込みます。途中で失敗しても、同じコマンドを再実行すれば収束します。トランザクションもロールバックもありません。

ソースディレクトリが「あるべき状態」

sourcePathは、/_artifacts/<site>/の下で配信する静的なツリーそのものです。公開コマンドは、そのサイトの接頭辞の中だけで、新しいものと変わったものを書き込み、無くなったものを消します。ほかのサイト、サイトの登録情報、アプリケーションプレーンには触れません。

  • HTMLとMarkdownは、そのまま配信できる状態にしておきます。ジェネレーターで作る場合は、先に実行して出力先のディレクトリを公開します。
  • .html、.htm、.mdはすべてインデックスに入ります。ディレクトリ名やドットファイルで除外することはありません。.gitは公開しません。
  • 受け付けるのは通常のファイルとディレクトリだけです。シンボリックリンクや特殊ファイルがあると、ソースのツリーの外へたどらずに公開を失敗させます。
  • sourcePathはいまのGitのチェックアウトの中になければなりません。updatedAtとコミッターはGitの履歴から取ります。履歴の無いファイルも公開できます。

変更の見つけ方

保存したオブジェクトには、中身のSHA-256をオブジェクトのメタデータ（artifact-pages-sha256）として付けています。計画を作るときは、あるべきオブジェクトを1つずつオリジンで調べ、このダイジェストとContent-Type、Cache-Control、エンコーディング、ディスポジションを比べます。違えば更新、無ければ作成、サイトの接頭辞にあるのに要らないものは削除です。

生成するindex.jsonとmeta.jsonにはgeneratedAtの時刻が入ります。ファイルが1つも変わっていなければ、計画ではこの項目を無視して保存済みのものを使います。同じソースを2回公開すると、2回目は本当にno-opになります。

ドライランは、設定、デプロイ済みのサイトの登録情報、保存済みのオブジェクトを読みますが、何も書き込まず、ロックも取らず、キャッシュの変更も依頼しません。結果はplannedかno-opです。--format jsonを付けると、パスごとのすべての変更、プレビューの一覧についての判断、依頼する予定のinvalidationPathsを出力します。

ターミナル
# 計画：読むだけ
$ artifact-pages site sync --site checkout --dry-run
# 同じ計画を適用する
$ artifact-pages site sync --site checkout

checkoutは説明用のサイトIDです。本文検索のデータも両方のコマンドが自動で生成します。検索とインデックスを参照してください。

書き込みの順序と、その間に読者が見るもの

書き込みは、まだ存在しないオブジェクトを指す状態を作らない順に行います。ファイル、内容で名前が決まる検索のblob、index.json、検索のマニフェストと続き、meta.jsonが最後です。古いオブジェクトは、新しいインデックスが指さなくなってから消します。

この順序で参照切れは減りますが、複数のオブジェクトの更新は不可分ではありません。短い間、古いメタデータと新しいファイルが同時に見えたり、新しいインデックスが出たあとも古いファイルが残っていたり、キャッシュから古い内容が返ったりします。バージョン1はこの結果整合性を受け入れています。版ごとのディレクトリも、サイトを一度に切り替えるポインターもありません。

失敗と再試行

公開は冪等な、あるべき状態への同期です。途中で失敗したら失敗を報告し、安全に止まれるならロックを解放します。同じコマンドを再実行すると、すべてのオブジェクトを確かめ直し、足りないものを書き、残ったものを消します。

止まった場所残る状態次の実行がすること
一覧の取得何も変わっていません。部分的な一覧から削除することはありません。一覧を最初から取り直します。
書き込みの途中新しい中身の一部が保存され、インデックスはまだ古いままです。一致するものは飛ばし、残りを書き、続けてインデックスとメタデータを書きます。
削除の途中新しいインデックスは公開済みで、古いオブジェクトが一部残っています。残った古いオブジェクトを消します。一括削除が一部だけ成功した場合も失敗として扱います。
キャッシュの依頼オリジンは更新済みで、再試行の記録にURLが残っています。オリジンに差分が無くても、残っている無効化を依頼し、no-opではなくsyncedと報告します。
プロセスの異常終了ロックが取られたまま残ります。ロックに有効期限はありません。一定時間待ってから失敗します。運用者が何も動いていないことを確かめ、lock inspectとlock recover --observed-etagでロックを解放します。

ロールバックが無い理由は、1回ごとの目的が「オリジンを1つのソースと同じにすること」だからです。失敗した実行の続きは、最初から実行するのと同じ操作になります。前の内容に戻したいときは、前の内容を公開します。収束の仕方は同じです。キャッシュ再試行の記録があるのは、CDNへの依頼が失敗してもオリジン側には比べる差分が残らないためです。記録には、オリジンにもう存在しないURLも含めて、まだ済んでいないURLを残します。

サイトのロックとサイトの登録情報の確認

サイトごとに小さなロックの記録_control/locks/sites/<site>.jsonが1つあり、site sync、preview publish、registry syncが共有します。記録は存在しないときだけ作り、変更はETagによる比較交換（compare-and-swap）でだけ行います。そのため、古い状態を見て復旧しようとした操作が、あとから取った別の持ち主のロックを解放してしまうことはありません。サイトが違えばロックも別なので、別々に公開できます。

サイトの登録情報の確認は、ロックを取ったあとに、キャッシュではなくオリジンのsites.jsonを直接読んで行います。「このソースは登録されているか」の確認と「オブジェクトを書く」の間に隙間ができません。別のリポジトリから公開する人は、管理者の設定のチェックアウトを必要とせず、デプロイ済みのサイトの登録情報を読めれば足ります。

これはArtifact Pagesのコマンド同士の調整で、セキュリティの境界ではありません。バケットへ直接書き込める認証情報を持つ人は迂回できます。認証情報の範囲を絞るのはプロバイダー側の設定の役目です。信頼モデルを参照してください。

site syncとregistry cleanupが重なったとき

registry syncは、まずデプロイ済みのサイトの登録情報からサイトを外して新しい公開の入口を閉じ、そのあと同じサイトのロックを取ってからサイトの接頭辞を消します。どちらが先に動いても、結果は同じ状態になります。

registry syncが成功を報告するのは、desired setの反映、オリジンからの削除、キャッシュの依頼がすべて成功したあとです。cleanup journalにより安全に再試行できます。これは結果整合性で、取り消しではありません。無効化が行き渡るまでエッジが古い応答を返すことがあり、すでにブラウザへ届いたページを取り戻すこともできません。サイトの登録情報の更新は、別に_control/locks/registry.jsonで1つずつ行います。
