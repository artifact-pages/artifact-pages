検索とインデックス

要点2種類の検索は、どちらも公開時に作ったファイルを使ってブラウザの中で動きます。名前で探す検索は、開いているサイトの成果物インデックスをメモリ上で順位付けします。本文検索は、分割済みの静的なインデックスのうち、確定した検索語に必要な部分だけをダウンロードします。検索サーバーはありません。

別々の2つの入口

名前で探す本文を検索する
場所コマンドパレット（⌘K / Ctrl K）サイドバーの入力欄（⌘⇧F / Ctrl ⇧ F）
使うデータ画面の移動のために読み込み済みのindex.jsonsearch/*。--fulltext付きで公開した場合だけ
動くとき入力のたびEnterで検索語を確定したときだけ
対象タイトル、パス、ファイル名タイトルと本文の静的なテキスト
並び順順位付けパス順。順位付けなし
範囲開いているサイトだけ

パレットから本文検索へ検索語を渡せます。検索語が空でなければ「Search page text for …」が候補に出て、⌘↵ / Ctrl ↵でも同じことができます。読者から見た操作は、ガイドの読者の体験にあります。

名前で探す

ブラウザがサイトの成果物インデックスを全件読み込むのは、そのサイトを開いたときだけで、ほかのサイトのインデックスは読みません。読み込んだあとの検索はページ内の計算だけなので、入力に合わせて結果がすぐ変わります。

  • 一致の仕方：タイトルとパスを空白、スラッシュ、ハイフンで語に分けます。入力した語の文字が、どれか1つの語の中に順番どおり含まれていれば一致です。語全体や先頭が一致するものほど高い点になります。たとえばpay flowでdesign/payment-flow.htmlが見つかります。
  • 順位：ピン留めしたページと最近読んだページを上げます。この情報は読者のブラウザの保存領域にあり、外へは出ません。文書が5,000件以上のサイトでは、公開時に計算した採点用のプロファイルをindex.jsonに加え、開いているページに近い語やフォルダも考慮できるようにします。
  • 何も入力していないときは、ピン留めしたページ、最近読んだページ、コマンドの順に並べます。
  • 範囲の切り替え：@は起動時に読み込んだ軽いサイトのメタデータを検索してサイトを切り替えます。#は、インデックスに記録したtocから、開いているページの見出しを検索します。>はコマンドを検索します。

サイトごとに1つの完全なインデックスにしている理由もあります。ベンチマーク（ローカルのヘッドレスChromium、合成データ、2026-09-25）では、20,000件のインデックスを分割して先読みしても、使えるようになるまでの時間もメモリも改善しませんでした。分割しない9.85 MBのインデックスは中央値606 ms、分割した場合は606〜621 msで使えるようになりました。1,000件のサイトが20個ある場合、開いているサイトのインデックスは486 KB、全サイトのメタデータの合計は3.7 KBで、中央値107.8 msで使えるようになりました。いずれもローカルでの計測で、CDNやネットワークの遅延を予測するものではありません。

本文検索

公開時に作るもの

本文検索は任意です。site publish --fulltext（ローカルで作るだけならindex build --fulltext）は、各文書から静的なテキストを取り出して正規化し、_indexes/<site>/search/に別の投影として書きます。meta.jsonのfullTextUrlがその場所を知らせ、index.jsonは変わりません。検索を残したい公開では、毎回このフラグを付けます。付けずに公開するとfullTextUrlは外れ、サイトの検索オブジェクトも消えます。

オブジェクト中身キャッシュ
search/manifest.json形式の版、文書数、rootとすべてのleafをまとめて表すgenerationのハッシュ、rootとちょうど128の区画への参照（URL、SHA-256、サイズ）変わりうる。s-maxage=60
search/root-<sha256>.gz語の辞書、1つの文書にしか出ない語（その文書を辞書の中に直接記録）、結果の順に並べたパスの表不変。1年
search/leaf-<sha256>.gzその区画に振り分けた語ごとの文書の集合。5通りの符号化のうち最も小さいもので保存不変。1年

ファイル名は中身のハッシュなので、変わらなかった区画は公開を繰り返してもURLが同じままで、キャッシュも効き続けます。保存時の型はapplication/octet-streamで、HTTPのContent-Encodingは付けません。ブラウザがファイルごとにSHA-256とサイズを確かめてから、自分で.gzを展開します。

Enterを押したときの流れ

  1. 入力欄に打っている間は何もダウンロードしません。Enterで検索語を確定します（IMEの変換を確定するEnterは除きます）。検索語はURLに?q=として残ります。
  2. 空でない最初の検索で、展開用のコードを必要になった時点で読み込みます。クライアントはマニフェスト（60秒たつと取り直す）とrootを取得します。
  3. 検索語に必要なleafだけを、同時に6つまで取得し、それぞれを検証します。区画が欠けていたり壊れていたりすればエラーにし、一部だけの結果を空として扱うことはありません。
  4. すべての文書を対象に検索語の結果を掛け合わせ、件数と、パス順に並べたIDの1ページ分（既定は20件）を返します。タイトルは読み込み済みのindex.jsonから取ります。
  5. 結果を開くと、HTMLでもMarkdownでも、CSS Custom Highlight APIで検索語を強調します。ページのDOMは変えません。URLにフラグメントがあるときや、読者がすでにスクロールしたときを除き、最初の一致までスクロールします。

一致の規則

  • 本文と検索語は同じ方法で正規化します。NFKCのあと小文字にし、空白をそろえます。検索語は空白で区切ります。
  • すべての語が一致した文書だけが見つかります（AND）。語の順序は問いません。文書の中の、空白で区切られた1つの語の一部分に含まれていれば一致です。そのため、日本語の辞書が無くても試行で再試行が見つかります。
  • フレーズの完全一致、入力ミスの許容、語幹の処理、同義語、意味（ベクトル）検索には対応しません。4,096文字を超える検索語は受け付けません。
  • インデックスに入るもの：HTMLのタイトルと静的な本文、Markdownのタイトルと描画したテキスト（コードブロックとリンクの文字を含む）。入らないもの：タイトル以外の<head>の中身、スクリプト、スタイル、template、noscript、hidden・aria-hidden="true"・data-search-ignoreの付いた要素。CSSによる表示・非表示や、スクリプトが作るテキストは評価しません。画像のaltとパスも本文のインデックスには入りません（パスは名前で探す検索が扱います）。

検索中に公開が入ったとき

公開では、検索のblobをindex.json、マニフェスト、meta.jsonより先に書き、古いblobはそのあとで消します。古いマニフェストを持ったままのブラウザが、消えたばかりのleafを取りに行くと404になります。その場合はマニフェストを1回だけ取り直し、検索全体をやり直します。結果のページをめくる間に検索データが変わったときは、世代を混ぜずに最初から取り直します。公開のほかの部分と同じく結果整合性で、トランザクションのようなスナップショットではありません。

トレードオフと計測値

  • 関連度の順位付けも抜粋もありません。インデックスに残すのは、ある語を含む文書がどれかだけで、位置や回数は残しません。そのため結果はフォルダごとにまとめ、パス順に並べます。
  • rootは必ず取得します。パスの表全体と、1つの文書にしか出ない語の辞書を含むので、一致が0件の検索でも、マニフェストの世代ごとに1回はダウンロードします。
  • 空白の無い長い日本語は、辞書の長い項目になります。部分一致の正しさは保たれますが、文書の間で項目を共有しにくく、空白のある文章ほどは小さくなりません。
  • 広い部分文字列は多くのleafに触れます。1回の検索で取得する量は、サイトの規模だけでなく検索語によっても変わります。

静的にしている理由

製品の原則は、ファイルとして配れるものは公開時に計算しておくことです。検索もこれに従っています。

  • 運用するものが無い。動かし、増強し、守り、同期を保つ検索クラスタはありません。検索データは、対象のページと同じsite publishが書き込み、ロックし、無効化し、削除します。
  • 配信の経路もアクセス制御も同じ。検索のファイルは/_indexes/<site>/にある普通のオブジェクトで、同じCDNから配信され、運用者がエッジでそのパスに設定したアクセス制御がそのまま効きます。
  • 使ったときだけ取得する。サイトを開いただけでは検索データをダウンロードしません。--fulltextを付けずに公開したサイトには検索データがありません。

その代わりに、上に挙げた制約があります。順位付け、抜粋、意味検索を加えるには、保存するデータを増やすか、検索時にモデルを動かす必要があり、いまの契約には含めていません。
