Previews

Short answerA preview publishes the changed documents of one Git head as an immutable revision addressed by its commit SHA, lists it in a small per-site catalog, and leaves its lifetime to the storage provider. Production publishing later removes catalog entries whose revisions are gone.

What gets previewed

A preview answers “what will these changed pages look like?”, not “what will the whole site look like after merging?”.

  • Selection: compare the merge base of the default branch's current HEAD (--default-ref, default origin/HEAD) and the preview head (--head, default HEAD) against that head. Only added or modified HTML and Markdown under the registered source path are previewed. A rename previews the new path; a deleted document has no preview.
  • Snapshot: every previewed byte comes from the head's committed tree, not a temporary merge with the default branch.
  • Outcomes: a change that only deletes documents returns no-preview; a change that touches only non-document files is an error.
  • Resources: local CSS, JavaScript (including static module imports, followed transitively), images, and fonts that a changed document needs are copied into the revision, keeping their relative layout. Names built at runtime can be added with --include PATH (exact paths or path.Match patterns). JavaScript-built root-relative URLs and arbitrary runtime navigation are outside the guarantee.

Records, keys, and routes

ObjectKeyContent
Revision files/_previews/<site>/revisions/<sha>/files/<path>The documents and resources, byte for byte from the head tree
Revision manifest/_previews/<site>/revisions/<sha>/manifest.jsonheadSha, defaultHeadSha, mergeBaseSha, createdAt, bundleDigest, files[] (path, SHA-256, content type), documents[]
Catalog/_previews/<site>/catalog.jsongroups[]: id (pr:<number> or head:<sha>), kind, headSha, optional prUrl, updatedAt, documents[]

The logical document route is /:site/_previews/<full SHA>/<document path>, and /:site/_previews is the site's Previews list. An optional ?group=pr%3A42 is reader context only: it never changes the revision or its bytes.

Revisions and groups

The two identities do different jobs.

REVISION = FULL HEAD SHA

A revision URL never changes content while the provider keeps it. Publishing the same head again verifies the stored objects instead of rewriting them; a different projection for the same head is an error. A direct URL resolves through its own manifest, not the catalog.

GROUP = WHAT DISCOVERY SHOWS

The catalog shows the latest completed revision per group. With an explicit --pull-request, the group is pr:<number>; without it, the preview is manual and its group is head:<sha>. Older revisions leave the catalog, but their direct URLs keep working while the objects exist.

PR provenance is never inferred from a branch, commit, or CI event. With --pull-request, the CLI reads the pull request through GitHub's API and checks its base repository, that the head is in the same repository, and the head SHA. Pull requests from forks are excluded. The reader shows a quiet header label with the short SHA, and a PR link only when the catalog confirms that the named group still points at that SHA.

Publication order and links

preview publish takes the same per-site lock as site publish and registry unregister, then rechecks the deployed registry. It uploads the revision files and its manifest as create-only objects, and only then reads and updates the catalog as an idempotent upsert by group. If the catalog update fails, the run reports failure and can be retried; uploaded objects that never reached the catalog are removed by provider retention like any others.

Inside a preview, a link to another changed document opens that document in the same revision; a link to an unchanged document opens its production route. HTML links move the reader app itself rather than nesting the app inside the frame.

Previews stay out of production views: they are not in index.json, Browse, Recently updated, page text search, or palette page results. The site home has a quiet link to the Previews list, and the palette has an “Open previews” command. Opening that list loads only this site's catalog.

Lifetime and cleanup

The provider owns preview lifetime. An administrator sets one preview_retention_days value in the infrastructure configuration (not the CLI config). It becomes an S3 lifecycle expiration on AWS or an R2 object-lifecycle rule on Cloudflare, applied to the whole _previews/ prefix. The app stores no expiry timestamp, runs no timer, and promises no exact deletion time.

Because provider deletion is asynchronous, a catalog can briefly point at an expired revision. Two things handle that:

  1. When the Previews list opens, the reader checks each candidate's manifest and hides missing ones. A missing preview document shows Preview unavailable with a way back to the site; a missing raw resource returns a real 404.
  2. Every site publish and preview publish reads the catalog at the origin under the site lock. A reference is removed only when its manifest is confirmed missing; a read error is not proof of absence. site publish writes the reduced catalog only after the production projection is committed, so a failed production publish never hides previews.

There is no PR-close workflow. Merged, closed, and manual previews stay discoverable while their manifests exist. registry unregister deletes a site's previews immediately along with the rest of its projection.

What has been proven

  • Proven locallyThe record contract, direct routes, encoded paths, same-head retry, and a manifest going missing (T1); missing manifests hidden and raw 404s (T4); concurrent group updates, interrupted publication, and both preview/unregister orderings (T5); resources, transitive modules, and changed/unchanged link routing (T6); pruning only confirmed-missing references through the local CLI (T8); and, with the real CLI, a local edge and the storage API, deleting one revision so that the next production publish prunes only that reference, a warm browser's list drops it, and its old URL shows “Preview unavailable” (T17, npm run test:preview-retirement).
  • Sampled on CloudflareOn 2026-10-01, a disposable site's manual preview rendered with its modules and resources, same-head retries returned no-op, a deliberately deleted manifest was pruned by the next production publish, and R2 reported the lifecycle rule on a preview object. On 2026-10-02, two new heads published concurrently through the CLI both stayed in the catalog, an interrupted publish recovered through lock recover with the observed ETag and a retry, and a stale process that had lost the lock was rejected before replacing the catalog. After one revision was deleted, the next production publish pruned only its reference and the browser list dropped it; the old URL showed “Preview unavailable” on a later reload, not instantly (T15).
  • Not yet provenActual provider lifecycle deletion timing (observation in progress), publishing from a real GitHub pull request and CI, and cleanup against AWS.
GUIDE

Previews follow the same access rules as everything else on the origin: an unguessable SHA is not access control. See Trust model and the guide's Access and trust.
