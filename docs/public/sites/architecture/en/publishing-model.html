Architecture · 03

Publishing model

Short answersite sync makes the stored site match one source directory. It compares the whole desired projection with what is already at the origin, writes the difference in an order that keeps references intact, and can simply be run again until the site converges. There is no transaction and no rollback.

The source directory is the desired state

sourcePath is the exact static tree to serve under /_artifacts/<site>/. Publishing uploads what is new or changed and deletes what is no longer there, within that site's prefixes only. It never touches another site, the registry, or the application plane.

  • HTML and Markdown must already be ready to serve. If they come from a generator, run it first and publish its output directory.
  • Every .html, .htm and .md file is indexed; no directory or dotfile heuristics exclude pages. .git is never published.
  • Only regular files and directories are accepted. A symbolic link or special file makes publishing fail instead of following it out of the source tree.
  • sourcePath must be inside the current Git checkout. Git history supplies updatedAt and the committer; files without history still publish.

How changes are detected

Each stored object carries the SHA-256 of its bytes as object metadata (artifact-pages-sha256). Planning looks up every desired object at the origin and compares that digest together with Content-Type, Cache-Control, encoding, and disposition. Anything that differs is an update, anything missing is a create, and anything listed under the site's prefixes but not desired is a remove.

The generated index.json and meta.json contain a generatedAt time. When no file changed, planning ignores that field and keeps the stored copy, so publishing the same source twice is a real no-op.

A dry run reads the config, the deployed registry, and the stored objects, but writes nothing, takes no lock, and requests no cache changes. It reports planned or no-op. With --format json it lists every per-path change, every preview catalog decision, and the invalidationPaths it would request.

TERMINAL
# Plan: reads only
$ artifact-pages site sync --site checkout --dry-run
# Apply the same plan
$ artifact-pages site sync --site checkout

checkout is an illustrative site ID. Page text search data is generated by both commands automatically; see Search and indexes.

Write order, and what readers may see meanwhile

Objects are written so that nothing refers to an object that does not exist yet: files first, then immutable search blobs, then index.json, then the search manifest, and meta.json last. Stale objects are deleted only after the new index no longer points at them.

This reduces broken references, but a multi-object update is not atomic. For a short window a reader may see old metadata with new file bytes, a new index while stale files are still being removed, or older content from a cache. Version 1 accepts this eventual consistency: there are no versioned release directories and no atomic site pointer.

Failure and retry

Publishing is idempotent desired-state synchronization. If a run fails partway, it reports the failure and releases its lock when it can stop safely. Running the same command again re-checks every object, finishes what is missing, and removes what is left over.

The process diesThe lock stays held. Locks do not expire.Waits for a bounded time, then fails. An operator confirms nothing is running and frees the lock with lock inspect and lock recover --observed-etag.

Why no rollback? Each run's goal is to make the origin equal to one source, so finishing a failed run is the same operation as starting it. To return to earlier content, publish that earlier content; the same convergence applies. The cache retry record exists because a failed CDN request leaves nothing at the origin to diff: it remembers the URLs still owed, including ones that no longer exist at the origin.

The site lock and the registry check

Each site has one small lock record, _control/sites/<site>/lock.json, shared by site sync, preview publish, and registry sync. It is created only if absent and changed only with a compare-and-swap on its ETag, so a recovery that inspected an old state cannot release a newer owner's lock. Different sites use different locks and publish independently.

The registry check runs after the lock is held and reads sites.json directly from the origin rather than a cached copy. That closes the gap between “is this source registered?” and “write the objects”. A publisher in another repository does not need the admin's config checkout; it only needs to read the deployed registry.

This is coordination between Artifact Pages commands, not a security boundary. Someone with direct write credentials to the bucket can bypass it. Scoping credentials is a provider setup concern; see Trust model.

Concurrent site sync and registry cleanup

registry sync first removes the site from the deployed registry, which closes the gate to new publishes, then takes the same site lock before deleting the site's prefixes. Either ordering ends in the same state.

Registry sync reports success only after desired-set reconciliation, origin cleanup, and the cache request have all succeeded. Its cleanup journal makes retries safe after registry omission. It is eventual consistency, not revocation: an edge may serve a stale response while invalidation propagates, and pages already delivered to a browser cannot be recalled. Whole-registry updates are serialized separately through _control/locks/registry.json.

What has been proven

  • Proven locallyWith deterministic local and fake backends (T14, T5): both site sync/registry cleanup orderings; failures injected during artifact upload, index.json and meta.json replacement, and partial stale deletion, each followed by a converging retry; aborting when either listing fails; AWS listing pagination and 1,000-key delete batches with per-object failures; guarded stale-lock recovery; a second process waiting on a held lock; and zero-document sites.
  • Sampled on CloudflareA disposable site was added to the desired set, synced, previewed, retried, and removed by registry omission against the live R2 deployment on 2026-10-01, and an R2 compare-and-swap race produced exactly one winner. On 2026-10-02, an interrupted preview publish left its lock held, lock recover with the observed ETag freed it, and the retry succeeded; a stale process that had lost the lock was rejected before replacing the catalog. Publishing with temporary scoped credentials (including the site lock and cache retry record) also worked (T15). These are samples, not the complete provider proof.
  • Not yet provenConcurrent site sync runs for different sites across processes against a real provider, and real S3 and R2 conditional-write and interruption-recovery runs of site sync with provider cache behavior (T14). No live AWS run.
