Architecture · 02

Storage layout

Short answerEverything a reader sees is a static object at a predictable key: one site registry, two small JSON documents per site, the site's files under their own prefix, and optional search and preview objects. Each class of object has its own cache rule.

The site registry: sites.json

The admin keeps the list of sites in the sites mapping of artifact-pages.yaml, reviewed in Git. registry register validates it and writes /_indexes/sites.json: an array sorted by site ID, so equivalent YAML always produces the same JSON. Nobody edits the JSON by hand.

/_indexes/sites.json
{
  "schemaVersion": 1,
  "sites": [
    {
      "id": "checkout",
      "name": "Payments / Checkout",
      "description": "Payment flow designs and incident reviews.",
      "repository": "acme/checkout",
      "sourcePath": "docs/artifacts"
    }
  ]
}

The same file serves two readers. The browser uses the IDs, names, and descriptions to list sites. The publisher uses repository and sourcePath to check that the checkout it is publishing from is the registered source. The file changes only when sites are registered or unregistered, not when someone publishes. The values above are illustrative.

Two documents per site: meta.json and index.json

Each site has a small discovery document and a full artifact index, with separate jobs.

META.JSON — SMALL, READ FOR EVERY SITE

The site's title and description, artifactCount, generatedAt, the artifactIndexUrl pointer to its index, and fullTextUrl when page text search is published. No artifact records.

INDEX.JSON — FULL, READ FOR THE ACTIVE SITE

One record per HTML or Markdown document: id and path (the exact source-relative path), title, format, artifactUrl, updatedAt, lastCommitter.name, source (repository, URL, ref, file path), and toc headings.

/_indexes/checkout/meta.json
{
  "schemaVersion": 1,
  "site": {
    "id": "checkout",
    "title": "Payments / Checkout",
    "description": "Payment flow designs and incident reviews."
  },
  "generatedAt": "2026-09-28T00:00:00Z",
  "artifactCount": 4,
  "artifactIndexUrl": "/_indexes/checkout/index.json",
  "fullTextUrl": "/_indexes/checkout/search/manifest.json"
}

The pointer fields keep the browser from hard-coding locations. A site with no documents is still published: its index has "artifacts": [] and its metadata reports "artifactCount": 0, which the reader shows as an empty site rather than an unpublished one.

  • A 404 for meta.json leaves the registered site listed as not yet published; any other metadata error leaves it listed with its details unavailable. One bad site never breaks the site list.
  • The display title comes from HTML <title> or the first Markdown H1, with a readable filename as the fallback. updatedAt and the committer come from Git history; files without history fall back to their modification time and have no committer.

What the browser loads, and when

Requests grow with what the reader does, not with how many sites exist. Only the active site's full index is ever downloaded.

The browser never lists storage. It does not call an object-storage listing API or depend on nginx autoindex; everything it needs to find is named in sites.json, meta.json, or index.json.

Artifact keys and routes

A file at docs/artifacts/design/flow.html in a site whose sourcePath is docs/artifacts is stored at /_artifacts/checkout/design/flow.html and opened at /checkout/design/flow.html. The directory structure and names are kept exactly, so relative links between a page and its CSS, scripts, images, and modules keep working.

  • Every .html, .htm and .md file is a page, including index.html and files in folders such as _includes/. Other files are copied and addressable but are not listed as pages.
  • Each path segment is percent-encoded once when building artifactUrl or a route, so spaces, #, ?, %, + and non-ASCII names round-trip. Filenames that are not valid UTF-8 are rejected.
  • Keep resources relative. A root-relative URL such as /assets/report.css starts at the origin root and leaves the site's namespace.
  • A missing resource is a real 404, not the app shell.

Each stored object gets its Content-Type from a fixed, case-insensitive extension map rather than the publishing machine's MIME database. Publishing never sets Content-Disposition: attachment and never claims a Content-Encoding the bytes do not have.

ExtensionsContent-Type
.html, .htmtext/html; charset=utf-8
.md, .markdowntext/markdown; charset=utf-8
.css / .js, .mjs, .cjstext/css; charset=utf-8 / text/javascript; charset=utf-8
.json, .mapapplication/json; charset=utf-8
.svgimage/svg+xml; charset=utf-8
Images, fonts, .pdf, .wasmTheir standard types (for example image/png, font/woff2, application/wasm)
Anything elseapplication/octet-stream (still copied and addressable)

Cache rules, and why

The two planes change on different schedules, so they get different rules. Mutable URLs are always revalidated by browsers; shared caches get a short, bounded lifetime; URLs whose name changes with their content are cached for a year.

ObjectCache-Control
/index.html, fixed-name app filesno-cache, max-age=0, must-revalidate
/assets/<name>-<8-character hash>.*public, max-age=31536000, immutable
sites.json, meta.json, index.json, search/manifest.jsonpublic, max-age=0, s-maxage=60, must-revalidate
/_artifacts/<site>/*public, max-age=0, s-maxage=300, must-revalidate
search/root-*.gz, search/leaf-*.gzpublic, max-age=31536000, immutable
Preview catalog.json / revision filess-maxage=60 / s-maxage=300, both with max-age=0, must-revalidate

Bounded freshness is only the fallback. After the origin is updated, site publish asks the CDN to invalidate exactly the URLs that changed, and keeps a retry record until that request succeeds (see Publishing model). A successful request still does not mean every edge has refreshed, and it cannot update a reader who already has the page open.

The local nginx analogue serves /_indexes/* with no-store so changes show immediately during development. The rules above are what publishing stores on each object and what provider delivery must honor; live Cloudflare responses for sampled index and artifact objects matched them (T15). Live AWS headers have not been observed yet.

The private control area

Coordination state lives under /_control/, outside every site's index and artifact prefixes, so cleaning a site never deletes it.

KeyPurpose
_control/locks/sites/<site>.jsonThe per-site lock shared by site publish, preview publish, and unregister. Kept (as free) even after the site is unregistered.
_control/locks/registry.jsonSerializes whole-registry updates.
_control/site-cache/<site>.jsonCache invalidation paths still owed after a failed publish.
_control/registry-cleanup.jsonContent cleanup still owed for sites removed from the registry.

Delivery must never return these bytes. Locally nginx answers /_control/* with 404; a provider route may instead return the app shell, which shows Page not found.
