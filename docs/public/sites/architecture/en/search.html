Search and indexes

Short answerBoth kinds of search run in the browser against files made at publish time. Finding a page by name ranks the active site's artifact index in memory. Page text search downloads only the parts of a static, sharded index that a committed query needs. No search server is involved.

The palette can hand a query to page text search: when the query is not blank it offers “Search page text for …”, and ⌘↵ / Ctrl ↵ does the same. How this looks to a reader is in the guide's Reading page.

Finding by name

The browser loads a site's full artifact index only when that site becomes active, and never reads other sites' indexes. Once it is loaded, searching is pure computation in the page, so results update as you type.

  • Matching: titles and paths are split into words at spaces, slashes, and hyphens. Each typed word must appear, letter by letter in order, inside one of those words, and exact and prefix matches score higher. So pay flow finds design/payment-flow.html.
  • Ranking: pins and recently read pages are lifted. These come from the reader's own browser storage and never leave it. For sites with 5,000 or more documents, the publisher adds a precomputed scoring profile to index.json so the palette can also weigh words and folders near the open page.
  • A blank query lists the reader's pinned pages, then recently read pages, then commands.
  • Scopes: @ searches the lightweight site metadata already loaded at startup and switches site; # searches headings of the open page, from the toc recorded in the index; > searches commands.

Why one complete index per site? A benchmark (local headless Chromium, synthetic data, 2026-09-25) found that splitting a 20,000-artifact index into eagerly loaded chunks did not improve ready-to-use time or memory: the monolithic 9.85 MB index was ready at a median of 606 ms, chunked variants at 606–621 ms. With 20 sites of 1,000 artifacts each, the active index was 486 KB and all sites' metadata together was 3.7 KB, ready at a median of 107.8 ms. These are local measurements, not a forecast of CDN or network latency.

Page text search

What publishing builds

Page text search data is generated by every site sync and local index build. The commands extract and normalize each document's static text and write a separate projection under _indexes/<site>/search/. meta.json advertises it with fullTextUrl; index.json is unchanged.

ObjectHoldsCache
search/manifest.jsonVersion, document count, a generation hash covering root and all leaves, and references (URL, SHA-256, sizes) to the root and exactly 128 shard slotsMutable, s-maxage=60
search/root-<sha256>.gzThe token dictionary, terms that occur in only one document (with that document inline), and the path table in result orderImmutable, one year
search/leaf-<sha256>.gzDocument lists for the tokens hashed to that shard, each stored in its most compact of five encodingsImmutable, one year

The files are named by the hash of their bytes, so an unchanged shard keeps its URL across publishes and stays cached. They are stored as application/octet-stream without HTTP Content-Encoding; the browser inflates the .gz itself after checking each file's SHA-256 and sizes.

What happens on Enter

  1. Typing in the field downloads nothing. Enter commits the query (an IME conversion Enter does not). The query is kept in the URL as ?q=.
  2. On the first non-blank search the decoder code is loaded on demand. The client fetches the manifest (refreshed after 60 seconds) and the root.
  3. It fetches only the leaves the query terms need, at most six at a time, and verifies each one. A missing or corrupt shard is an error, never an empty partial result.
  4. It intersects the terms over the complete document set and returns the total plus one page of IDs (20 by default) in path order. Titles come from the already loaded index.json.
  5. Opening a result highlights the terms in the HTML or Markdown page with the CSS Custom Highlight API, without changing the page's DOM, and scrolls to the first match unless the URL has a fragment or the reader has already scrolled.

Matching rules

  • Text and query are normalized the same way: NFKC, then lowercase, with whitespace folded. The query is split on whitespace.
  • Every term must match (AND), in any order. A term matches when it is a substring of one whitespace-separated token in the document, so 試行 finds 再試行 without a Japanese dictionary.
  • Not supported: exact phrases, typo tolerance, stemming, synonyms, or semantic (vector) search. A query longer than 4,096 characters is rejected.
  • Indexed: the HTML title and static body text; the Markdown title and rendered text, including code blocks and link labels. Skipped: <head> content other than the title, scripts, styles, template, noscript, and elements marked hidden, aria-hidden="true", or data-search-ignore. CSS visibility and text created by scripts are not evaluated; image alt text and paths are not part of the text index (paths are covered by finding by name).

Updates while someone is searching

Publishing writes search blobs before index.json, the manifest, and meta.json, and deletes old blobs afterwards. A browser still holding an older manifest whose leaf was just deleted gets a 404, reloads the manifest once, and reruns the whole search. If the search data changes between pages of results, the list is fetched again from the start rather than mixing generations. Like the rest of publishing, this is eventually consistent, not a transactional snapshot.

Trade-offs and measurements

  • No relevance ranking and no snippets. The index stores which documents contain a token, not where or how often, so results are listed in path order, grouped by folder.
  • The root is always fetched. It holds the complete path table and the one-document vocabulary, so even a query with no matches downloads it once per manifest generation.
  • Long unspaced Japanese becomes long dictionary entries. Substring matching stays correct, but sharing between documents, and therefore size reduction, is weaker than for spaced text.
  • Broad substrings can touch many leaves. The payload of a query depends on the query, not only on the site size.

Why it is static

The product rule is to compute at publish time whatever can be served as a file. Search follows it:

  • Nothing to operate. There is no search cluster to run, scale, secure, or keep in sync. The search data is published, locked, invalidated, and deleted by the same site sync as the pages it describes.
  • The same delivery and the same gate. Search files are ordinary objects under /_indexes/<site>/, served by the same CDN and covered by whatever access control the operator configures at the edge for that path.
  • Pay only when used. Opening a site downloads no search data; search data is fetched only after a reader submits a page-text query.

The cost is the set of limits above. Ranking, snippets, and semantic search would need more stored data or a model run at query time, and are not part of the current contract.
