How Git Artifact Pages works

Short answerGit holds the source. Each site publishes from its own repository, separately from every other site, into one shared static projection in object storage. One static reader app in the browser reads that projection and presents every site the same way. No application server sits in the request path.

Git is the source; the website is a projection

Artifacts are made and reviewed in the repository that produces them, and Artifact Pages never edits them. A site is registered as one pair of repository and source directory (repository, sourcePath). Publishing reads that directory in a Git checkout, builds the site's index, and copies the files unchanged. It does not run templates, bundle CSS or JavaScript, or rewrite links.

Everything served to the browser is reproducible projection data. The reader app, the object storage, and the CDN are not systems of record. If a published object goes missing or a publish stops halfway, publishing the same source again brings the site back to the same state. How that convergence works is on Publishing model.

Independent publishing, shared experience

Publishing has no central step. An admin deploys the reader app and registers each site once in the sites mapping of artifact-pages.yaml; neither operation builds any site's content. From then on, each site's repository runs site publish from its own CI whenever its content changes. A run writes only that site's prefixes, /_indexes/<site>/ and /_artifacts/<site>/, under that site's own lock, so it neither rebuilds nor waits for any other site.

WhoCommandWritesWhen
Adminapp deployThe application planeWhen the reader app is upgraded or rolled back
Adminregistry register/_indexes/sites.jsonWhen the set of sites changes
Each site's repositorysite publishThat site's /_indexes/<site>/ and /_artifacts/<site>/Whenever that site's content changes, on its own schedule

What the sites share is the layout of the static projection and the reader app that reads it. Every site's output follows the same object layout, and the app finds sites through /_indexes/sites.json and each site's small meta.json. Independently published sites therefore appear as one Artifact Pages space instead of separate websites. The site picker, file tree, command palette, page text search (on sites published with it), pins and recent reads, the reader, Contents and Details, and links to previews and to Git work the same on every site. Search stays within the site being read.

Two planes, plus a private area

The served origin is split by how often things change. The application plane is the reader app; it changes when an operator upgrades it. The content plane is the published sites; it changes every time someone publishes. The two are deployed independently: upgrading the app does not touch site objects, and publishing a site does not touch the app.

Logical routes and storage paths

Readers use and share only three kinds of URL. Storage paths are internal and are not the navigation model.

RouteShowsExample (illustrative)
/Site selection/
/:siteThe site's home/checkout
/:site/*One document/checkout/design/flow.html

For /checkout/design/flow.html, the edge returns the app shell. The app reads /_indexes/sites.json and the site's small meta.json, loads /_indexes/checkout/index.json because checkout is now the active site, and finally loads /_artifacts/checkout/design/flow.html into an iframe.

  • Filenames and extensions stay in the route. flow.html and flow.md are two different pages, and index.html is opened by name; a folder URL never opens it implicitly.
  • Each path segment is percent-encoded once, so spaces, #, ?, % and non-ASCII names keep their meaning. Names are never slugified.
  • A site is a logical namespace, not a repository. The repository is recorded as metadata (the Details panel shows it) and does not appear in the URL, so a site can move between repositories without changing its links.

What the edge does

The serving layer needs only path-based routing. Object paths go to storage; everything else falls back to the app shell.

RequestResult
/_indexes/*, /_artifacts/*, /_previews/*, /assets/*The stored object. A missing object is a real 404, not the app shell, so a broken relative link in an artifact fails visibly.
/_control/*Never the control object. The delivery layer may answer with the app shell, which shows Page not found, but must not return lock or retry-record bytes.
Anything elseThe app shell /index.html, which resolves the logical route in the browser.

Locally this is nginx in Docker Compose (docker/nginx/default.conf). The AWS reference deployment uses CloudFront in front of a private S3 bucket read through Origin Access Control. The Cloudflare deployment uses its Cache/CDN in front of R2 on a custom domain, with transform rules that rewrite logical routes to /index.html.

Why there is no request-time server

The design rule is static by default, build-time over request-time. Anything that can be computed when publishing is computed then and stored as a file:

  • Titles, paths, headings for Contents, last-update times and committers come from the source and Git history and are written to index.json.
  • The site list is a JSON file generated from the admin's config, not a directory listing. The browser never calls a storage listing API or relies on nginx autoindex.
  • Page text search, when enabled, is a set of static files built at publish time. See Search and indexes.

The result is that any static host with a CDN can serve the product, scaling is the CDN's job, and there is no database, server-side rendering, or search API to operate. The costs are deliberate: a change becomes visible only after it is published and caches revalidate, and there is no per-viewer logic. Who may read is decided at the edge, as described on Trust model.

What has been proven where

The repository is in its local-product phase. The contract above is proven locally first; provider delivery is checked separately and is not complete.

  • Proven locallyThe reader, nginx routing, committed fixtures, and registered-site publishing to a local storage directory. Emulator profiles (MinIO for the S3 API shape, fake-gcs-server for the gcp-local profile) prove adapter and HTTP contracts, not equivalence with real CloudFront, Cloudflare, or GCP services.
  • Sampled on CloudflareOn 2026-10-01 and 10-02, live checks on the Cloudflare deployment observed logical routes returning the app shell, real 404s for missing objects, the cache headers, and the production and preview CSP headers. Disposable sites were taken through publish, preview, and unregister, concurrent preview publishes and interruption recovery, publishing with scoped credentials, and a runtime HTTP request refused by the CSP. These are samples; the provider-delivery verification (T15) is still in progress.
  • Not yet provenLive AWS delivery (CloudFront and S3), actual preview lifecycle deletion timing, provider race and recovery cases such as concurrent publishes for different sites, and GitHub OIDC. Each page states its own open items.
