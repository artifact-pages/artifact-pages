Trust model

Short answerPublishing is the trust decision. Published HTML is approved, executable content rendered on the app's own origin in an unsandboxed iframe; Markdown is sanitized and never runs scripts. Who may read is decided by the operator's edge or network, not by Artifact Pages.

Publishing is the trust decision

Git Artifact Pages exists to show HTML reports, dashboards, and diagrams exactly as their authors built them, scripts included. It therefore treats published HTML as approved executable content, the way a team trusts its own internal web pages. The operator decides who may publish (people, CI workflows, credentials); the product does not try to make hostile HTML safe to view.

This is a deliberate fit for one organization, or several teams that trust each other, publishing to one origin. It is not designed for mutually untrusted publishers.

HTML: same origin, no sandbox

The reader loads /_artifacts/<site>/<path> into an ordinary iframe without a sandbox attribute, from the same origin as the app. That keeps relative URLs, ES modules, fonts, and fetches working exactly as when the file is opened directly, and keeps the artifact's CSS from leaking into the app.

The consequence is spelled out in the specification: an artifact's scripts can access the parent application's DOM, its local storage, and any other same-origin content. The reader keeps pins, recently read pages, and the theme in local storage, so an artifact could read or change them. These documentation pages use this on purpose: their script reads the reader app's theme from the parent page so they match it, and the reader in turn reaches into the frame to highlight page text search terms.

The per-site Content Security Policy

The edge sends an enforced CSP with every artifact response. Locally, nginx builds it from the request path:

Content-Security-Policy · /_artifacts/checkout/…
default-src http://localhost:4179/_artifacts/checkout/ https: data: blob:;
script-src  http://localhost:4179/_artifacts/checkout/ https: 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval' data: blob:;
style-src   http://localhost:4179/_artifacts/checkout/ https: 'unsafe-inline' data: blob:
  • Allowed: resources under the page's own site path, and any HTTPS origin (CSS, scripts, images, fonts, media, fetch), subject to normal TLS, CORS, and mixed-content rules. Inline scripts, styles, and eval stay allowed because artifacts are trusted.
  • Blocked: insecure external http: resources.
  • Not a cross-site wall. The https: source matches every HTTPS URL, including other sites' paths on the app's own origin once it is served over HTTPS. So in production one site's page can load another site's files. Over plain HTTP locally, the path source does block other sites' paths. 'self' is deliberately not used, because all sites share one origin. Allowed HTTPS resources may also redirect anywhere on HTTPS.

Practical consequence: each site carries its own copies of shared files. These documentation sites, for example, keep a copy of the same site.css and site.js in each site's assets/ rather than loading one site's files from another, so they work under both the local and the production policy.

Markdown: sanitized, never executed

Markdown follows a different model. The app renders it into its own DOM after passing embedded raw HTML through a sanitizer that removes script-bearing and disallowed elements and attributes. Publishing Markdown never grants script execution.

  • Mermaid diagrams render locally with securityLevel: "strict" and no diagram interactions; if rendering fails, the source stays visible as code.
  • Relative resources resolve from the Markdown file and must stay inside that site's artifact namespace. External links and images must be HTTPS; data: is allowed only for base64 PNG, JPEG, GIF, WebP, or AVIF images; mailto: links are allowed.
  • Links to other pages in the same site become app routes; other links open in a new tab with noopener and noreferrer.

Previews carry the same trust

Preview HTML is rendered under exactly the production model: same origin, unsandboxed iframe, the same resource rules scoped to the revision's path. Running preview publish approves that content before merge; it is not a safe viewer for arbitrary changes. That is why the trust gates sit at the input:

  • Only heads in the site's registered repository are previewed; pull requests from forks are excluded, even when they target a registered repository.
  • A privileged pull_request_target workflow must not check out and run fork content.
  • No preview-only hostname, no srcdoc fallback, and no blanket Access-Control-Allow-Origin: null or wildcard CORS grant.

Supporting fork previews or mutually untrusted publishers would need a separate approval and isolation model, such as a separate origin. That would be a new product decision.

Who may read is decided at the edge

Artifact Pages has no viewer accounts, logins, sessions, roles, or per-site access policy. If content must be restricted, the operator configures that at the hosting edge or the surrounding network: VPN or IP restrictions, Basic authentication, an identity provider with CloudFront signed cookies, Cloudflare Access, or an equivalent. Once a request is admitted, everyone gets the same static content.

Why keep identity out of the product?

  • The product stays static. There is no session to check, so any CDN can cache and serve every object, and there is no identity-aware cache partitioning to get wrong.
  • The operator chooses the mechanism. Each organization can use the gate that fits its provider and identity setup, protecting a hostname, selected paths, or a whole network, without the product defining an identity policy.
  • One boundary covers everything. A single gate in front of the origin protects pages, indexes, search data, and previews alike.

For that to hold, the gate must cover the logical routes and the raw /_indexes/*, /_artifacts/*, and /_previews/* paths, and run before protected bytes come from the origin or a shared cache. Several things are explicitly not access control:

  • Removing a site from the registry or hiding it from navigation; direct object URLs still work until the objects are deleted.
  • An unguessable preview SHA, or a preview being “before merge”.
  • Unregistering as revocation: it deletes origin objects and requests cache invalidation, but cannot recall bytes already delivered.

Publisher credentials and control objects

The registry check and the site lock coordinate Artifact Pages commands; they are not a permission system, and anyone with direct write credentials to the bucket bypasses them. Narrowing what a publisher can touch is the job of provider credentials: a satellite publisher should be able to read only the registry object; read, write, and delete only within its own site's index and artifact prefixes; read and write its preview prefix (the AWS reference policy withholds deletion of preview history); read and write its site lock _control/sites/<site>/lock.json; read, write, and delete its cache retry record _control/sites/<site>/site-cache.json; and request CDN invalidation (CloudFront CreateInvalidation, or a Cloudflare zone token with cache purge permission), because a publish that changes content purges the changed URLs. It never writes the registry or the application plane. Cloudflare supports this with an optional separate registry-reader identity; the AWS reference design intends GitHub Actions OIDC with separate admin and satellite roles.

Private coordination objects under /_control/* must never be returned to viewers. Delivery may answer those paths with the app shell, as long as the lock and retry-record bytes are never served.

What has been proven

  • Proven locallyIframe CSS containment, intended parent-DOM and storage access from benign fixtures, Markdown script removal, same-origin module loading without a null or wildcard CORS grant, external HTTPS allowed and external HTTP blocked by the CSP (T4, T6, ISSUE-037 browser cases).
  • Sampled on CloudflareOn 2026-10-01: an enforced artifact CSP header on live Guide HTML, a revision-scoped enforced CSP on preview HTML, and control-key paths returning only the app shell. On 2026-10-02: on the live Guide page, a fetch to an HTTP URL built at runtime was refused by the enforced CSP (connect-src via the default-src fallback, in Chromium), and temporary scoped R2 credentials were denied writes outside their site while still publishing it (T15).
  • Not yet provenThe external-HTTP refusal across the full matrix of resource types and browsers, isolating the cache-purge token from publisher processes, GitHub OIDC roles, and anything on live AWS.
