Git Artifact Pages / UI concept review

A wider set of calm, document-first directions.

The same artifact data can feel like a library, a changelog, a workbench, or a focused reader. This gallery makes those choices visible before we commit to a product shell.

  • English product copy
  • No persistent site sidebar
  • Site switcher in the top bar
  • Command K remains available
  • Quiet navigation over ornament

01 / Site home

What should the site root feel like?

Every option keeps the site root as an artifact index. The difference is whether it optimizes for scanning, comparison, visual grouping, or recency.

Shared constraint The current site is selected in the top bar. There is no permanent list of sites competing with the content.

02 / Artifact view

How much navigation should surround the document?

These options all keep rendered artifacts in an iframe. The decision is about how much context remains visible while reading a single artifact.

Shared constraint The document remains the visual center. Navigation can recede, stay local, or become a deliberate second pane.

03 / Search and switching

What does ⌘ K actually search?

The shortcut can be a local navigation tool or a universal entry point. Both keep site switching out of the left rail; the scope is the important choice.

Interaction question Should search start inside the current site, or should it search every indexed site and make the site boundary part of each result?

04 / Decision surface

One glance across the tradeoffs.

No single pattern wins every workflow. This matrix is a prompt for choosing a small combination, not a vote for one complete design.

Suggested next step Pick one site-home pattern, one artifact-view pattern, and one search scope to combine into the next interactive prototype.

Pattern comparison

“Strong” means the pattern naturally supports the behavior. “Mixed” means it can work but needs additional controls. “Weak” means the behavior is deliberately not the focus.
